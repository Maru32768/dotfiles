# 設計の根拠

規則を足すとき、消すとき、測り直すときに読む。

## docs-redesignと分けた理由

docs-redesignは、文書そのものを変える。確かめるのは、組み立て直した後に技術的な記述が落ちていないこと。このスキルは元の文書を変えず、細部を省いた派生の文書を1つ作る。確かめるのは、書いた主張が元の文書と合うこと。約束も検査も違うので、スキルを分けた。見出しの一覧(`outline.sh`)と読者テストの資料(`reader-test.md`)は、docs-redesignのものを使う。

文の推敲は`prose-polish`が持つ。このスキルは文の規則を持たない。

## 調べた実装

2026-11-14に、公開されているスキルと、手元に入っているスキルを読んだ。公開のものは、サブエージェントがその日のデフォルトブランチから取得した。表に書いた点は、保存した本文を親が検索して確かめた。ライセンスはGitHubのAPIが返したもの。どれも基盤にはせず、文も写していない。借りたのは考え方だけ。

| 実装 | ライセンス | していること | 借りたこと | 採らなかったこと |
|---|---|---|---|---|
| github/spec-kitの`analyze` | MIT | 仕様、計画、タスクを読むだけで照らす。要求にIDを振って在庫を作り、対応の穴を挙げる | 元を変えずに読むこと。書く前に在庫(台帳)を作ること | 仕様を新しく書く流れの中の段で、既にある文書の概観は作らない |
| Fission-AI/OpenSpec | MIT | 変更を、proposal、specs、design、tasksの層に分けて書く | 1つの文書が抱える仕事を層に分けて見ること | 新しく書くための型 |
| bmad-code-org/BMAD-METHODの`bmad-shard-pro` | APIは判定できなかった | 長い文書を、文を変えずに分割し、分けた後に元へ戻せるかを検査する | 元の文を変えないこと。変えていないことを機械で確かめること | 分割そのもの。このスキルは元のファイルに触れない |
| mizchi/skillsの`extract-glossary` | 検出されなかった | 用語を抜き出し、確かめたもの、推測、要確認に分ける。1つの図は10ノード前後にする | 図の節点の数の目安。確かめたことと推測を分けること | 用語集を作って置くこと |
| microsoft/apmの`pr-description-skill` | Apache-2.0 | PR本文を書き、Mermaidを`mmdc`で検査する | 図の構文を道具で検査すること | PR本文が対象 |
| RicoSuter/Namotion.Interceptorの`pr-review-story` | MIT | 差分のすべてのhunkがちょうど1回現れることをスクリプトで確かめ、推測に印を付ける | 推測に印を付けること | 差分が対象。概観は全部を載せない |

| liza-mas/lizaの`adr-backfill` | Apache-2.0 | gitの履歴と文書からADRを掘り起こす | 無い | 文書を新しく書く |
| pstackの`how`と`teach`(手元の0.9.86) | 確かめていない | コードを探って、仕組みの説明を返す。部品が多いときは、1枚の図にまとめない | 1つの図を1つの話題にすること | 対象はコードで、既にある文書ではない。図を元と照らす手順は無い |

既にある仕様書や設計文書から、読む前の概観を作るスキルは見つからなかった。図の中身を元の文書と照らすスキルも見つからなかった。

## 根拠にした資料と、使わなかったもの

使った。親が元のページか要旨で確かめたものと、サブエージェントの報告のままのものがある。それぞれに書く。

- 仕様の前に読む文書は、制度として既にある。W3C TAGのexplainerの手引き(https://w3ctag.github.io/explainer-explainer/ )は、提案の節にWebIDLを入れないよう求め、explainerを今の状態を書く文書として扱う(親が確かめた)。RustのRFCはGuide-levelとReference-levelを節で分け、TC39の提案はREADMEと仕様文を別のファイルにする(サブエージェントの報告)。概観に規範の細部を写さず、節へ案内する規則にした。
- LLMの要約は、元より広く言う。科学の文章の要約4900件で、DeepSeek、ChatGPT-4o、LLaMA 3.3 70Bは26〜73%で一般化しすぎた(Peters and Chin-Yee、arXiv 2504.00025、親が要旨で確かめた)。量を表す語、条件、例外を残す規則と、独立の照合を入れた。
- LLMに要約の忠実さを採点させても、人の注釈と強くは合わない(FABLES、arXiv 2404.01261。26冊、3,158の主張という数は親が要旨で確かめ、この結果はサブエージェントの報告)。照合では質を採点させず、主張ごとに、挙げた行で言えるかを判定させる。
- 関連する箇所を先に抜き書きさせると、長い文書への質問の正答率が上がった(Anthropicの実験、https://www.anthropic.com/research/prompting-long-context 。Claude 2で0.939から0.961。例を添えた効果を含み、要約の実験ではない。親が確かめた)。概観を書く前に台帳を作る手順にした。
- LLMの描く図は、記法に合っていても、中身が元と合わないことがある。クラス図では、構文より意味、特に関係の生成が弱い(OODEval、arXiv 2601.07602。29のLLMという数は親が要旨で確かめ、この結果はサブエージェントの報告)。要求からのシーケンス図でも、網羅と正しさに問題が多い(Ferrari ほか、arXiv 2404.06371、28文書。サブエージェントの報告)。図は節点と線の一覧から描き、線ごとに元の行を付け、照合で線を1本ずつ見る。
- 図が文章より設計の理解を助けるという証拠は弱い。Heijstek ほか(ESEM 2011、47人)では、図と文章のどちらも設計判断を伝える効率で優れなかった。Jolak ほか(EMSE 2020、学生240人)では、図は対面の議論と細部の想起を促した(どちらもサブエージェントの報告で、親は元を読んでいない)。図は2つまでにし、文章の代わりにしない。
- AIが作る文書がたまり、古く矛盾した仕様が残ることが警告されている(Thoughtworks Technology Radar、2026-11-04、「AI-driven documentation sprawl」をCautionに置く。親が確かめた)。概観は既定で使い捨てにし、置くときは元のコミットとsha256を記す。
- 文書は、ソースから消えたコード要素を参照し続ける(Tan ほか、arXiv 2212.01479、3,000を超えるプロジェクト。親が要旨で確かめた)。概観で名指しする識別子を、コードで確かめる。

使わなかった。

- Mermaidの生成のベンチマークの、構文の点(MermaidSeqBench、arXiv 2511.14967)。構文までLLMの審判が採点している。構文は、パーサーで確かめれば済む。
- 主張の照合に専用のモデルを使うこと(MiniCheck、arXiv 2404.10774)。道具を増やさず、別のエージェントに任せた。
- 概観の質の採点。上のFABLESの結果による。
- 設計文書や仕様書の要約を測った研究は、見つからなかった。上の研究の対象は、科学の文章、物語、質問応答、要求からの図で、設計文書の概観に当てはまるかは分からない。

## 試作(2026-11-14)

題材は、Javaのライブラリの設計文書(709行、英語)。親が全文を読み、台帳(46行)を作り、台帳だけから日本語の概観(図は2つ)を書いた。その後、別のopusに、概観の主張を1つずつ元の文書と照合させた。

| 見たもの | 結果 |
|---|---|
| 照合(直す前の概観、143件) | 支持138、言い過ぎ3、不支持2、行が違う0、出どころ無し0。このほかに、誤解につながる省き方5件 |
| 親による確かめ | 10件とも、元の行を読むと指摘の通りだった。14か所を直した。直した後の文は、親が読んだだけ |
| 機械の検査 | 挙げた行がリンク先の節の範囲に入るか(直す前59件、後70件)、アンカーがGitHubのページにあるか(36個)。不一致0 |
| 識別子 | 概観で名指しした27個が、どれもコードにあった |
| 図 | Mermaid 10.9.1の`parse`と`render`を、2つとも通った。GitHubでの描画は確かめていない |
| 元の文書の食い違い | 2件見つけた。直さずに、概観の最後に挙げた |

台帳から書いても、誤りは出た。規則にしたこと。

- 言い過ぎは、元に無い「だけ」を足した文、例外を落とした文、元の「応じて」を「数だけ」に強めた文だった。量を表す語と例外の規則にした。
- 不支持は、「3つの層」と書いて表が4行だったことと、図の線のラベルが別の処理のことを書いていたこと。図を、線ごとに元の行を付けた一覧から描く規則にした。
- 省き方の5件は、どれも、ある設定や種類でだけ成り立つことを、いつも成り立つように読ませていた。照合の判定の件数には入らないので、照合のプロンプトで別に挙げさせる。

読者テストも1回行った。別のopusが、元の文書だけから問い14個と正解を作り、sonnetの読者2人が答えた。片方には直す前の概観だけを、もう片方には元の文書の冒頭50行と見出しの一覧だけを渡した。採点は親。

| 答えが文書にある12問 | 概観だけ | 冒頭50行と見出しだけ |
|---|---|---|
| 答えのある節を当てた | 10 | 8 |
| 渡した資料だけで正しく答えた | 8 | 3 |
| 誤答 | 0 | 0 |
| あるのに「文書に無い」と答えた | 1 | 1 |

- 差が大きかったのは、節を当てることより、理由や代償を尋ねる問いに資料だけで答えられたことだった。
- 概観の読者が「無い」と誤った問いは、概観が省いた例外についての問いだった。読者は、概観に書かれていないことを、元にも無いと読んだ。冒頭の断り書きと、「Aはできる」と書いたら元にある「Bはできない」も書く規則を足した。直した後では試していない。
- サブエージェントのトークンは、照合が約119k、問い作りが約95k、読者が2人で約158k。親の分は別。読者テストを頼まれたときだけにしたのは、この費用による。

## 検証(2026-11-15)

題材は、同じライブラリの別の設計文書(484行、英語)。2つの版を作らせた。

| 版 | 作り方 |
|---|---|
| スキル | opusのサブエージェントに、依頼の1文と、このスキルを読む指示を渡す。スキルの4の照合も、そのエージェントが別のエージェントに任せた |
| スキル無し | 同じ依頼の1文だけを渡す |

2つの概観を、別々のopusに、同じ指示で元の文書と照合させた。どちらがスキルの版かは伝えていない。スキル無しの版は行を挙げない文が多いので、判定を、中身(支持、言い過ぎ、不支持)と行(合う、違う、挙げていない)に分けた。コードについての主張と、概観そのものについての文は数えていない。

| | スキル | スキル無し |
|---|---|---|
| 概観の行数 | 132(リンクの定義を除いて116。上限は121) | 74 |
| 図 | 1 | 0 |
| 判定した単位 | 90 | 72 |
| 支持 | 90 | 65 |
| 言い過ぎ | 0 | 7 |
| 不支持 | 0 | 0 |
| 行が合う、違う、挙げていない | 74、0、16 | 41、1、30 |
| 誤解につながる省き方 | 0 | 1 |
| 書き手のトークンと時間 | 約140k、約11分 | 約87k、約1分 |

- スキル無しの版の言い過ぎ7件は、親が元の行を読んで確かめた。どれも、元にある限定(できる限り、リテラル先頭のコマンドでは、強い理由が無い限り、任意の、など)が落ちていた。照合は、このうち2件を軽いとした。
- スキルの版は、スキルの中の照合の指摘を直した後のもの。その照合は129件を判定し、言い過ぎ1、不支持1、行が違う1、出どころ無し3と、誤解につながる省き方1件を挙げた。直す前の版は、独立の照合にかけていない。
- 独立の照合は、スキルの版にも細かい違いを1つ記録した(判定は支持のまま)。決定の欄の「フォールバックを入れない」は、元では、今の実装には要らない、という書き方だった。同じ行の代償の欄が、将来の条件を補っている。スキル無しの版の同じ箇所は、言い過ぎと判定された。照合のエージェントは版ごとに別なので、厳しさは揃っていない。
- 親は、スキルの版の言葉の節と決定の表から12の主張を選び、元の行を読んだ。どれも合っていた。
- 元の文書のsha256は、前後で同じだった。
- スキルの版の図は、Mermaid 10.9.1の`parse`と`render`を通った。確かめたのは親で、書き手は`mmdc`が無く、検査していないと報告した。節へのリンクのアンカー15個は、GitHubが返すHTMLにあった。
- スキルの版の時間は、スキル無しの約8倍だった。書き手のトークンに、照合のエージェントの分が入っているかは分からない。独立の照合は、1回に約100kかかった。

表示用のHTMLは、表、正しい図、構文の誤った図、生のHTML、`javascript:`のリンクを入れたMarkdownで、ブラウザで試した。

- CSPとSRIの下で、`marked`と`mermaid`が読み込まれ、表と図が描かれた。構文の誤りは冒頭に出た。
- インラインのイベントハンドラと`javascript:`のリンクは、動かなかった。
- 生の`<meta http-equiv="refresh">`は、CSPでは止まらず、2秒後に別のサイトへ移動した。そこで、生のHTMLを文字として出すようにした。直した後は、移動しない。
- 試したのは、httpsのページに同じHTMLを書き込んだ場合。`file://`で開いた場合は、確かめていない。

検証の後で、スキルの文を直した。書き手が迷った点(食い違いを控える基準、長さの数え方、アンカーの確かめ方、利用者向けの資料の範囲、照合で数えないもの)を具体的にした。直した後では、試していない。

限界。

- 題材は1つで、版ごとに1回しか試していない。
- 書き手と照合が、同じ系列のモデルである。
- 照合が見るのは、書かれた主張が元と合うかだけ。スキル無しの版は、元の文書の分かりにくい箇所(前置きの無い例など)を挙げていた。スキルの版には無い。こうした違いは、上の数に出ない。
- 人が読んで把握しやすいかは、測っていない。

測り直すときは、上の作り方と測り方をそのまま使う。

# 設計の根拠

規則を足すとき、消すとき、測り直すときに読む。

## docs-redesignと分けた理由

docs-redesignは文書そのものを変える。確かめるのは、組み立て直した後に技術的な記述が落ちていないこと。このスキルは元の文書を変えず、細部を省いた派生の文書を1つ作る。確かめるのは、書いた主張が元の文書と合うこと。約束も検査も違うので、スキルを分けた。見出しの一覧(`outline.sh`)は、docs-redesignのものを使う。読者テストの資料(`reader-test.md`)は使わない。その資料は文書の前の版と後の版を比べる手順で、概観には当てはまらないので、手順をSKILL.mdに書いた。

文の推敲は`prose-polish`が持つ。このスキルは文の規則を持たない。

## 調べた実装

2026-11-14に、公開されているスキルと、手元に入っているスキルを読んだ。公開のものは、サブエージェントがその日のデフォルトブランチから取得した。手元のものは、親が読んだ。表に書いた点は、保存した本文を親が検索して確かめた。ライセンスはGitHubのAPIが返したもの。どれも基盤にはせず、文も写していない。借りたのは考え方だけ。

|---|---|---|---|---|
| github/spec-kitの`analyze` | MIT | 仕様、計画、タスクを読むだけで照らす。要求にIDを振って在庫を作り、対応の穴を挙げる | 元を変えずに読むこと。書く前に在庫(台帳)を作ること | 仕様を新しく書く流れの中の段で、既にある文書の概観は作らない |

## 根拠にした資料と、使わなかったもの

使った。親が元のページか要旨で確かめたものと、サブエージェントの報告のままのものがある。どちらなのかを、それぞれに書く。

- 仕様の前に読む文書は制度として既にある。W3C TAGのexplainerの手引き(https://w3ctag.github.io/explainer-explainer/ )は、提案の節にWebIDLを入れないよう求め、explainerを、今の状態を書く文書として扱う(親が確かめた)。RustのRFCはGuide-levelとReference-levelを節で分け、TC39の提案はREADMEと仕様文を別のファイルにする(サブエージェントの報告)。概観に規範の細部を写さず、節へ案内する規則にした。
- LLMの要約は元より広く言う。科学の文章の要約4900件で、DeepSeek、ChatGPT-4o、LLaMA 3.3 70Bは26〜73%で一般化しすぎた(Peters and Chin-Yee、arXiv 2504.00025、親が要旨で確かめた)。量を表す語、条件、例外を残す規則と、独立の照合を入れた。
- LLMに要約の忠実さを採点させても、人の注釈と強くは合わない(FABLES、arXiv 2404.01261。26冊、3,158の主張という数は親が要旨で確かめ、この結果はサブエージェントの報告)。照合では質を採点させず、主張ごとに、挙げた行で言えるかを判定させる。
- 関連する箇所を先に抜き書きさせると、長い文書への質問の正答率が上がった(Anthropicの実験、https://www.anthropic.com/research/prompting-long-context 。Claude 2で0.939から0.961。例を添えた効果を含み、要約の実験ではない。親が確かめた)。概観を書く前に台帳を作る手順にした。
- LLMの描く図は記法に合っていても、中身が元と合わないことがある。クラス図では、構文より意味、特に関係の生成が弱い(OODEval、arXiv 2601.07602。29のLLMという数は親が要旨で確かめ、この結果はサブエージェントの報告)。要求からのシーケンス図でも、網羅と正しさに問題が多い(Ferrariほか、arXiv 2404.06371、28文書。サブエージェントの報告)。図は節点と線の一覧から描き、線ごとに元の行を付け、照合で線を1本ずつ見る。
- 図が文章より設計の理解を助けるという証拠は弱い。Heijstekほか(ESEM 2011、47人)では、図と文章のどちらも、設計判断を伝える効率で他方より有意には優れなかった。Jolakほか(EMSE 2020、学生240人)では、図は対面の議論と細部の想起を促した(どちらもサブエージェントの報告で、親は元を読んでいない)。図は2つまでにし、文章の代わりにしない。
- AIが作る文書がたまり、古く矛盾した仕様が残ることが警告されている(Thoughtworks Technology Radar、2026-11-04、「AI-driven documentation sprawl」をCautionに置く。親が確かめた)。概観は既定で使い捨てにし、置くときは元のコミットとsha256を記す。
- 文書はソースから消えたコード要素を参照し続ける(Tanほか、arXiv 2212.01479、3,000を超えるプロジェクト。親が要旨で確かめた)。概観で名指しする識別子を、コードで確かめる。

使わなかった。

- Mermaidの生成を測るベンチマークの、構文の点(MermaidSeqBench、arXiv 2511.14967)。構文までLLMの審判が採点している。構文はパーサーで確かめれば済む。
- 主張の照合に専用のモデルを使うこと(MiniCheck、arXiv 2404.10774)。道具を増やさず、別のエージェントに任せた。
- 概観の質の採点。上のFABLESの結果による。

設計文書や仕様書の要約を測った研究は、見つからなかった。上の研究の対象は科学の文章、物語、質問応答、要求からの図で、設計文書の概観に当てはまるかは分からない。

題材はJavaのライブラリの設計文書(709行、英語)。親が全文を読み、台帳(46行)を作り、台帳だけから日本語の概観(図は2つ)を書いた。その後、別のopusに、概観の主張を1つずつ元の文書と照合させた。

|---|---|
| 照合(直す前の概観、143件) | 支持138、言い過ぎ3、不支持2、行が違う0、出どころ無し0。このほかに、誤解につながる省き方5件 |
| 親による確かめ | 10件とも、元の行を読むと指摘の通りだった。14か所を直した。直した後の文は、親が読んだだけ |
| 機械の検査 | 挙げた行がリンク先の節の範囲に入るか(直す前59件、後70件)、アンカーがGitHubのページにあるか(36個)。不一致0 |
| 識別子 | 概観で名指しした27個が、どれもコードにあった |
| 図 | Mermaid 10.9.1の`parse`と`render`を、2つとも通った。GitHubでの描画は確かめていない |
| 元の文書の食い違い | 2件見つけた。直さずに、概観の最後に挙げた |

台帳から書いても、誤りは出た。規則にしたこと。

- 言い過ぎは、元に無い「だけ」を足した文、例外を落とした文、元の「応じて」を「数だけ」に強めた文だった。量を表す語と例外の規則にした。
- 不支持は、「3つの層」と書いて表が4行だったことと、図の線のラベルが別の処理のことを書いていたこと。図を、線ごとに元の行を付けた一覧から描く規則にした。
- 省き方の5件はどれも、ある設定や種類でだけ成り立つことを、いつも成り立つように読ませていた。照合の判定の件数には入らないので、照合のプロンプトで別に挙げさせる。

読者テストも1回行った。別のopusが元の文書だけから問い14個と正解を作り、sonnetの読者2人が答えた。片方には直す前の概観だけを、もう片方には元の文書の冒頭50行と見出しの一覧だけを渡した。採点は親。

| 答えが文書にある12問 | 概観だけ | 冒頭50行と見出しだけ |
|---|---|---|
| 答えのある節を当てた | 10 | 8 |
| 渡した資料だけで正しく答えた | 8 | 3 |
| 誤答 | 0 | 0 |
| あるのに「文書に無い」と答えた | 1 | 1 |

- 差が大きかったのは、節を当てることより、理由や代償を尋ねる問いに資料だけで答えられたことだった。
- 概観の読者が誤って「無い」と答えた問いは、概観が省いた例外についての問いだった。読者は概観に書かれていないことを、元にも無いと読んだ。冒頭の断り書きと、「Aはできる」と書いたら元にある「Bはできない」も書く規則を足した。直した後では試していない。
- サブエージェントのトークンは、照合が約119k、問い作りが約95k、読者が2人で約158k。親の分は別。読者テストを頼まれたときだけにしたのは、この費用による。

## 検証(2026-11-15)

題材は同じライブラリの別の設計文書(484行、英語)。2つの版を作らせた。

| 版 | 作り方 |
|---|---|
| スキル | opusのサブエージェントに、依頼の1文と、このスキルを読む指示を渡す。スキルの「4. 確かめる」の照合も、そのエージェントが別のエージェントに任せた |
| スキル無し | 同じ依頼の1文だけを渡す |

2つの概観を、別々のopusに、同じ指示で元の文書と照合させた。どちらがスキルの版かは伝えていない。スキル無しの版は行を挙げない文が多いので、判定を中身(支持、言い過ぎ、不支持)と行(合う、違う、挙げていない)に分けた。コードについての主張と、概観そのものについての文は数えていない。

| | スキル | スキル無し |
|---|---|---|
| 概観の行数 | 132(リンクの定義を除いて116。上限は121) | 74 |
| 図 | 1 | 0 |
| 判定した単位 | 90 | 72 |
| 支持 | 90 | 65 |
| 言い過ぎ | 0 | 7 |
| 不支持 | 0 | 0 |
| 行が合う、違う、挙げていない | 74、0、16 | 41、1、30 |
| 誤解につながる省き方 | 0 | 1 |
| 書き手のトークンと時間 | 約140k、653秒 | 約87k、77秒 |

- スキル無しの版の言い過ぎ7件は、親が元の行を読んで確かめた。どれも、元にある限定(できる限り、リテラル先頭のコマンドでは、強い理由が無い限り、任意の、など)が落ちていた。照合はこのうち2件を軽いとした。
- スキルの版は、スキルの中の照合の指摘を直した後のもの。その照合は129件を判定し、言い過ぎ1、不支持1、行が違う1、出どころ無し3と、誤解につながる省き方1件を挙げた。直す前の版は独立の照合にかけていない。
- 独立の照合はスキルの版にも細かい違いを1つ記録した(判定は支持のまま)。決定の欄の「フォールバックを入れない」は、元では、今の実装には要らない、という書き方だった。同じ行の代償の欄が将来の条件を補っている。スキル無しの版の同じ箇所は、言い過ぎと判定された。照合のエージェントは版ごとに別なので、厳しさは揃っていない。
- 親はスキルの版の言葉の節と決定の表から12の主張を選び、元の行を読んだ。どれも合っていた。
- 元の文書のsha256は前後で同じだった。
- スキルの版の図は、Mermaid 10.9.1の`parse`と`render`を通った。確かめたのは親で、書き手は`mmdc`が無く、検査していないと報告した。節へのリンクのアンカー15個は、GitHubが返すHTMLにあった。
- スキルの版の時間は、スキル無しの約8倍だった。書き手のトークンに、照合のエージェントの分が入っているかは分からない。独立の照合は1回に約100kかかった。

### 表示用のHTML

入力は`tests/ci/docs-overview-browser-check.md`にある。表、リスト、リンク、図(正しいもの、構文の誤ったもの、`mermaid`の勧告に倣ったもの)、生のHTML、消毒を抜こうとする入力を入れてある。ブラウザで試した結果を、直した順に書く。

- CSPとSRIの下で、`marked` 12.0.2と`mermaid` 10.9.8が読み込まれ、表と図が描かれた。構文の誤りは冒頭に出た。
- インラインのイベントハンドラと`javascript:`のリンクは、動かなかった。
- 生の`<meta http-equiv="refresh">`はCSPでは止まらず、2秒後に別のサイトへ移動した。`marked`が生のHTMLを文字に変えるようにすると、この入力では移動しなくなった。
- レビューで、その直し方を抜ける入力が見つかった。`marked` 12.0.2は、`<code>`か`<kbd>`の開始タグの後ろの文字をエスケープしない。`/`で区切ったタグは、そこでなければエスケープされるが、そこではそのまま出力に残る。この入力では、`<meta>`、画面を覆う`<a>`、`<img>`が文書に入り、ページが移動した。
- そこで、`marked`の出力を動かない文書(`DOMParser`)で解析し、決めた要素(見出し、段落、リスト、表、コード、強調、取り消し線、リンク、引用、区切り線、改行)と、決めた属性(`http://`か`https://`で始まるリンク先、コードの言語、表の揃え、番号つきリストの開始番号)だけを移すようにした。直した後は、上の入力で移動しなかった。文書に入ったのは、決めた要素と属性だけだった。
- 別のモデルのレビューで、消毒の根が上書きされうる、と指摘された。HTMLの仕様では、文書の`body`は`name="body"`の`<form>`や`<img>`で上書きされる。そうなると、消毒されない要素が文書に入る。Chromium 152では、`DOMParser`の文書でこの上書きは起きなかった。ほかのブラウザは確かめていない。`<form>`のプロパティの上書きは起きた。`<input name="replaceWith">`があると、消毒が例外で止まり、何も入らずにMarkdownのまま表示された。根を`<template>`の断片に替え、要素を文字に替える呼び出しを`Element.prototype`から取った。直した後は、この入力でも止まらずに表示された。
- 今の版では、決めた要素のほかは、文字として出る。画像とチェックボックスのリスト(`- [ ]`)も、`marked`が`<img>`と`<input>`にするので、文字として出る。相対パスと`javascript:`のリンクは、リンク先が外れ、地の文と同じ色の文字になる。先頭に置いた`<meta>`と`<style>`も、文字として出る。`<frameset>`のタグは消える。
- 図のSVGは、`mermaid`が文書に直接入れる。上の消毒は通らない。初めに固定した`mermaid` 10.9.1には、公開済みの勧告が当たっていた。シーケンス図のラベルのXSS(GHSA-7rqq-prvp-x9jh)は10.9.4で、状態図の`classDef`からのHTMLの注入(GHSA-ghcm-xqfw-q4vr)は10.9.6で直っている。10.x系で最新の10.9.8に上げた。10.9.8では、上の入力でページは移動せず、図の中に`<meta>`とイベントの属性は無かった。フローチャートのラベルに書いた`<img>`は、`onerror`を外されて図の中に残った。読み込みはCSPが止めた。10.9.1で同じ入力がどう動くかは、試していない。
- 図の中身の安全は、`mermaid`のstrictの設定とCSPに頼っている。固定した版は自動では上がらない。
- 試したのは、Claudeのデスクトップアプリの内蔵ブラウザ(Chromium 152)で、httpsのページに同じHTMLを書き込んだ場合。`file://`で開いた場合と、ほかのブラウザは、確かめていない。
- 確かめ方を1度誤った。同じタブにHTMLを書き直すと、前のページのCSPが残って重なり、新しい版の`mermaid`の読み込みが止まる。前のページが読み込んだ`mermaid`が残って動くので、止まったことに気づかなかった。10.9.8の確かめは、新しいタブでやり直した。入力のファイルに、この注意を書いた。
- CIではブラウザを動かせない。`tests/ci/docs-overview-test.sh`は、確かめた版のインラインのスクリプトのハッシュを固定している。スクリプトを変えたら、上の入力で確かめ直す。

### スキルの文の直し

検証の後で、スキルの文を直した。書き手が迷った点(食い違いを控える基準、長さの数え方、アンカーの確かめ方、利用者向けの資料の範囲、照合で数えないもの)を具体的にした。レビューの後にも直した(読者テストの手順をスキルの中に書いた、節の参照に名前を添えた、照合に渡す写しを作る手順を足した、識別子を確かめる段を概観を書いた後へ移した、リンクの規則を元がpushされていない場合まで書いた)。どちらも、直した後では試していない。

### 限界

- 題材は1つで、版ごとに1回しか試していない。
- 書き手と照合が、同じ系列のモデルである。
- 照合が見るのは、書かれた主張が元と合うかだけ。スキル無しの版は元の文書の分かりにくい箇所(前置きの無い例など)を挙げていた。スキルの版には無い。こうした違いは上の数に出ない。
- 人が読んで把握しやすいかは、測っていない。

測り直すときは、上の作り方と測り方をそのまま使う。

## 文書の束(2026-11-15)

束の手順(`bundle.md`)は2つの束で1回ずつ試して決めた。

- **題材。** thomvaill/log4brainsの`docs/adr`(コミット`17e3202`、Apache-2.0)は、ADRが11本で400行。どの文書にも`Status`と`Date`の欄があり、置き換えの組が2つある。CommandLibの`docs/design`(コミット`4edf11e8`)は、設計文書が12本で3,639行。`Status:`の行を持つ文書は2本で、日付は無い。
- **作り方。** 束ごとに、`SKILL.md`と`bundle.md`の下書きだけを読ませたエージェント(opus)に概観を作らせた。エージェントは手順どおりに照合のエージェントを自分で起こし、指摘を直した。
- **測り方。** 書き手が直した後の概観の全体を、親が別のエージェント(opus)に、`bundle.md`の照合のプロンプトで照合させた。指摘は親が元の行で確かめてから直し、直した行だけを新しいエージェントに照合させた。この直しと照合を2回繰り返した。

|---|---|---|

分かったこと。

- log4brainsの置き換えの2組は、「置き換えられた決定」に入り、「今有効な決定」には入らなかった。1組では、置き換えが古い文書にしか書かれていなかった。新しい文書は前の決定に触れるが、題もファイル名も挙げていない。
- CommandLibは、12本のうち10本が状態を述べていない。直した後の「今有効な決定」の32行のうち、25行の状態が「記載なし」になった。表の前の断りが無いと、有効だと確かめた決定のように読める。
- 文書の間の食い違いが、log4brainsで1件、CommandLibで3件挙がった。CommandLibでは、文書の中の食い違いも4件挙がった。全体の照合は、どの食い違いも支持と判定した(log4brainsの1件には書き方への注意が付いた)。
- 書き手が自分の照合で直した後にも、親が起こした照合は指摘を挙げた。CommandLibの不支持2件のうち1件は、理由の欄に理由ではなく方針を書いた行だった。もう1件は、状態が「記載なし」の文書に目的を述べる文がある、という指摘で、状態の定義に合わないので採らなかった。照合のプロンプトに状態の定義を足した。
- 親は直すときに新しい誤りを入れた。直した行の照合が挙げた不支持2件は、どちらも親が書いた文だった。1件は、理由の欄を「記載なし」とした文だが、挙げた範囲に理由が書かれていた。もう1件は、省いたものの説明に、案の評価が無い文書を入れた文だった。1行を根拠に足した限定は、同じ文書の別の節と食い違って読める、と指摘された。
- 照合を重ねても、指摘は0にならなかった。理由の欄の「記載なし」を、ある照合は支持とし、次の照合は不支持とした。照合は3回で止め、争いのある行は主張を削って節へ案内する形にした。最後の直しは、親が元の行を読み直しただけで、エージェントに照合させていない。
- エージェントが使ったトークンは、書き手が14万(log4brains)と24万(CommandLib)、全体の照合が11万と21万だった。直した行の照合は、1回につき1つのエージェントが2つの束を見て、1回目が15万、2回目が11万だった。どれも通知に出た値で、書き手が中で起こした照合の分は含まない。行を絞っても、照合のエージェントは1回の起動で10万を超えた。

実行の後で直した手順。直した後の手順では、概観を作り直していない。

- IDの振り方(日付の接頭辞は番号にしない)と、行の挙げ方(1つの括弧にまとめる)。
- 状態の定義(目的を述べる文は状態にしない、決定ごとの状態があればそれを使う)と、関係の定義(題、ファイル名、番号、リンクで挙げたものだけ。束の外は入れない)。
- 図にする境目。log4brainsでは、関係のある文書の組が2つなのに、3本の線の図が描かれた。組が3つ以上のときだけ図にする。
- 索引の状態の欄と日付の欄の、出どころの書き方。束の長さの上限が、`SKILL.md`の上限の代わりになること。
- 照合のプロンプトで`verify.md`のどの段を差し替えるかと、状態の定義。
- 理由の欄を「記載なし」と書かないこと、範囲や確度の断りが要る決定を表に入れないこと、指摘を直すために足す文を元の行で確かめること(`verify.md`)。
- 識別子を確かめるコードが手元に無いときの扱い(`SKILL.md`)。
- レビューで直した規則。状態の分け方(廃止、下書き、予定の決定を有効な決定に入れない)、推奨の扱い、名前を挙げない置き換えの言及、束に入れなかったファイルの確かめ、分けた束の置き換え、目印のgrep、小さい束の長さ、IDと日付の決め方。

限界。

- 束ごとに1回しか試していない。直した後の手順では、概観を作り直していない。
- 提案の段階や取り下げの文書がある束、通し番号を持つ束、40本を超える束は、試していない。CommandLibは2,000行を超えるが、書き手は台帳づくりをサブエージェントに分けず、自分で読んだ。束の読者テストも行っていない。
- 文書1つにつき決定を3つまで、長さを文書の数×12行まで、という数は、この2つの束に合わせて決めた。CommandLibの概観は上限の144行に達した。
- 束の外の文書に書かれた置き換えは見ない。
- 書き手と照合が、同じ系列のモデルである。照合どうしで判定が割れた。人が読んで把握しやすいかは、測っていない。

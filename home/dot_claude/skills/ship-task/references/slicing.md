# スライスの分け方

## 条件

スライスは、次の4つをすべて満たす。

1. 完了条件を、テストの名前かコマンドで言える
2. 上のスライスを全部捨てても、デフォルトブランチは壊れず、入れた意味がある
3. その振る舞いのテストを、同じスライスに持つ。テストを最後のスライスに回さない
4. 1文で言える

大きさは規則にしない。手書きで800行を超えそうなら割れないかを一度考え、100行未満には割らない。どちらも、過去の作業の単位とレビューの固定費からの目安で、根拠は弱い。小さく割るほど、review-loopの固定費が単位の数だけかかる。

## スライスの型

| 型 | 使う場面 | 完了条件の例 |
|---|---|---|
| 準備 | 振る舞いを変えないリファクタ | 既存のテストが全部通る |
| 契約 | 公開API、スキーマ、型、エラーの種類を先に固める。ライブラリではこれを先頭に置き、破壊的な変更にするか、非推奨の期間を置くかをここで決める | 契約を固めるテスト |
| 閉じた部品 | 入出力が閉じた純粋なロジック(文の分割、パーサ、変換) | 性質のテストと、生成した入力 |
| 垂直スライス | 利用者に見える機能を、端から端まで薄く通す | 実際の画面かCLIでの確認 |
| 移行の段 | expand、呼び出し側の移行、contract | 各段が単独で緑になる。一時的な互換層には、消す条件を書く |
| 基盤 | CI、ビルド、隔離 | 実際の環境での検査 |

## 先に決めることと、後に回すこと

- 計画の段で決める: スライスの間の契約(関数や型の名前とシグネチャ、スキーマ、エラーの種類、CLIの引数)、不変条件、互換性の方針、順序と依存、各スライスの完了条件
- 実装のときに決める: スライスの中の構造、ファイルの割り方、テストの細部

## スライス表

列は、番号、1文の説明、型、完了条件(検査のコマンド)、依存するスライス、状態(未着手、実装中、レビュー中、着地済み)。issueの本文に置く。

## 順序と並列

- 既定は直列に進める。前のスライスを着地させてから、次に着手する。
- 並列にしてよいのは、契約を共有しないスライスだけ。別のセッションと別のworktreeで進める。ファイルが別でも、同じ契約に触れる並列の変更は壊し合う。
- 前のスライスがレビューを待っている間に、それに依存する次のスライスを進めたいときだけ、前のブランチの上に積む。各スライスを今のデフォルトブランチから始めても、どの順でも入れられるなら、積まずに独立させる。

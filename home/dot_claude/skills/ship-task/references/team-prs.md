# チームのPR(ベースPR、子issue、QA)

ベースPRに子PRを集め、QAをベースPRで1回だけ行う決まりのリポジトリで使う。本文の型は`split-pr-stack/references/templates.md`にある。

型は、既にあるPRを分けるときのもの。ここでは元のPRが無いので、次のように読み替える。

- ベースPRの概要の「#<元 PR> は 1 本の PR としては大きすぎたため、<N> 本の子 PR に分けた」は、「#<元 issue>を、スライス表の<N>個のスライスに分けて進める」にする
- 子PRの「この PR の位置」の「#<元 issue> の実装（#<元 PR>）を分割した子 PR の <N> 本中 <n> 本目」は、「#<元 issue>のスライス表の<N>個のうち<n>個目」にする
- ベースPRの「子 PR」の節の、2本目以降の子PRが1つ下の子PRのブランチに向く、という文は、前のスライスに依存して積んだ子PRだけに当てはまる。ベースブランチに向く子PRがあれば、その文を直す
- `{{…}}`は`publish.sh`が埋めるものなので、ここでは手で埋める。`{{VERIFY}}`は、SKILL.mdの3のPR本文のEvidenceと同じく、`evidence.sh`の`table`の出力で埋める。`{{NEXT}}`は、次のスライスの子PRを作ったときに、1つ下の子PRの本文を直して埋める(「なし(スタックの一番上)」で埋めてあっても直す)。最後のスライスの子PRでは、作るときに「なし(スタックの一番上)」で埋める。ベースPRの表の`{{PR:<層>}}`は、子PRを作るたびにベースPRの本文を直して埋める。公開した本文を直すときは、`split-pr-stack`の6に従う
- 埋め残しは、最後のスライスの子PRを作り、ベースPRの表を埋め終えた後に、ベースPRとすべての子PRの本文で確かめる。`body=$(gh pr view <番号> --json body --jq .body) && ! grep -E '[{][{][A-Z]+(:[^{}]*)?[}][}]' <<<"$body"`が成功すればよい。`gh`が失敗したときにも、何も出ないのを埋め残しなしと読まない。途中では、後で埋める`{{NEXT}}`と`{{PR:<層>}}`が残っているのが正しい。`publish.sh`はこの検査を自分で行うが、手で埋めるときは誰も行わない

## スライス表が承認されたら

スライスが1つでも、同じように子issueとベースPRを作る。そのときは表の承認が無いので、作る子issueとベースPRを見せ、起票の前に承認を1回取る。チームの決まりが1本のPRを許すなら、型をPRにする。

- スライスごとに子issueを作り、元のissueのサブissueにする(`gh issue create --parent <元のissue>`)。担当、ボード、Sprintは元のissueに揃える。下書きは見せずに起票してよい。
- 子issueの本文には、そのスライスの完了条件と、依存する子issueを書く。依存する番号を書けるよう、依存の順に起票する。
- 統合用のベースブランチを作り、空のコミットを1つ置いて、ベースPRをDraftで作る(GitHubは差分の無いPRを作れない)。push、ベースPRの作成の前に確認を取る。

## スライスごとに

- 後からスライス表に足した行も、承認の後、着手の前に子issueを起票し、ベースPRの表に行を足す。
- 最初の子PRを作る前に、子PRをDraftにするか、Assigneesを誰にするかを利用者に確かめる。
- 子PRのbaseは、ベースブランチにする。前のスライスに依存し、前の子PRがまだベースにマージされていなければ、前のブランチをbaseにする。
- 本文は子PRの型で書く。`{{VERIFY}}`を埋める前の`check`、書いた後の「なぜ」の確かめ方、`prose-polish`は、SKILL.mdの3の「PRの本文」と同じにする。ベースPRの本文も、作るときと直すときに`prose-polish`にかける。

## マージまで

- 子PRは、レビューで承認されてから、確認を取り、スライス表の順に、merge commitでマージする。上のPRを先にマージすると、その変更はベースではなく下のPRのブランチに入る。
- 積んだ子PRでは、下の子PRをマージした後、上の子PRのbaseがベースブランチに付け替わったかを確かめる。ブランチが自動で消えない設定では付け替わらないので、`gh pr edit <番号> --base <ベースブランチ>`で付け替えてからマージする。付け替えても検査が始まらなければ、SKILL.mdの3のPRの型と同じく、ベースブランチを上のブランチへマージしてpushする。
- `Closes`はデフォルトブランチに向けたPRでしか効かないので、子issueは、子PRをベースにマージした時点で手で閉じる。
- マージの前に、CIが走るなら緑であることを確かめる。必須チェックは子PRにかからないことがあり、赤でもマージできてしまう。CIが走らないなら、その子PRの今の先端で、review-loopの検証コマンドを回して確かめる。
- QAはベースPRでまとめて行う。QAで見つけたバグは、ベースブランチに向けた子PRで直す。QA OKになり、すべての子PRがベースに入った後のSKILL.mdの4の突き合わせも通ったら、確認を取ってから、ベースPRをmerge commitでデフォルトブランチへマージする。

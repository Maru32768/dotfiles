# タスクの進め方

各段階の中身は既存のスキルに任せる。このスキルが持つのは、段階の順番と、各段階を飛ばすか、止まって確認するかの判断だけ。

## 0. 起点を固める

`gh issue view <N>` で、完了条件、未決事項、blocked by を読む。次のどれかに当たれば、要件が曖昧とみなして設計議論に入る。

- 未決事項が残っている
- 完了条件が、検証できる形になっていない
- 設計の選択肢が開いていて、issue からは選び方が決まらない

設計議論は、セッションのモデルを Fable にして行う。grill-me は利用者との対話なので、サブエージェントには任せられない。モデルの切り替えは、アプリのモデル選択で利用者に頼む。

- 対象の領域に仕様書や ADR があれば grill-with-docs、なければ grill-me で詰める
- 決まったことは、issue の本文（未決事項、完了条件）に書き戻す。モデルを戻した後は、ここが唯一の引き継ぎ点になる
- issue の書き換えは、確認を取ってから行う

曖昧でなければ、この段階は飛ばす。

## 1. 実装

- `pstack:poteto-mode` で進める。ブランチは 1 本にして、最後まで一気に実装する
- コミットは関心ごとに分けておく（振る舞いを変えないリファクタ、API 契約、テストやビルドの基盤、機能）。3 で層を切るときの材料になる
- この段階では PR を作らない。分けると決まれば、大きい PR は要らなくなる

## 2. レビュー

1. `review-loop` を収束するまで回す
2. 収束したら、Fable を 2 人目のレビュアーとして 1 回だけ読ませる
   - Agent ツールに `model: "fable"` を渡す
   - 渡すのは差分と変更の意図だけにする。review-loop の結論は渡さない。同じ前提に引きずられると、2 人目の意味がなくなる
3. Fable の指摘は、直す前に自分で再現する。直したら、その変更に review-loop を 1 ラウンドだけかける

## 3. 出し方の判断

次のすべてに当たれば、PR を作らずデフォルトブランチ（master や main）に直接入れる。

- デフォルトブランチへの直接の push が、ブランチの保護などで禁止されていない
- 関心ごとが 1 つ
- 手書きの差分が 100 行ほどまで（生成物は数えない）
- 公開 API、スキーマ、権限、隔離に触れない

直接入れるときは、ブランチをデフォルトブランチへ早送りでマージし、push の前に確認を取る。issue は push した後に閉じる。4 から 6 は飛ばす。

当たらなければ PR にする。次のどれかに当たれば分ける。

- 手書きの差分が 400 行を超える（生成物は数えない）
- 性質の違う変更が混ざっている（リファクタ、API 契約、テストやビルドの基盤、機能）
- 読み手の専門が分かれる（specs、例外処理、外部連携など）

どれにも当たらなければ、PR を 1 本作って終わる。

分けるときは `ronny:engineering-small-prs` で層を設計し、次の 2 つの表を作って利用者の承認を取る。

- 層の表: 順番、内容、依存する層、手書きの行数
- ファイルの持ち主の表: 変更した全ファイルについて、どの層が変えるか。複数の層が変えるファイル（共有ファイル）をここで洗い出す

## 4. 子 issue の起票

- 分割案が承認されたら、下書きを見せずに起票してよい
- 層ごとに issue を作り、元の issue のサブ issue にする（`gh issue create --parent <元の issue>`）。担当、ボード、Sprint は元の issue に揃える
- 本文には、その層が担う完了条件（元の issue の完了条件を層に配ったもの）と、依存する issue を書く
- 依存する issue の番号を本文に書けるよう、依存の順に起票する

## 5. ブランチと PR

`split-pr-stack` に従う。ブランチを作って検証した後、push と PR の作成の前に確認を取る。

## 6. マージまで

- 子 PR は表の番号順に、merge commit でマージする
- 子 issue は、子 PR をベースへマージした時点で手で閉じる
- QA はベース PR でまとめて行う。QA OK になったら、ベース PR を merge commit で main へマージする

# タスクの進め方

各段の中身は既存のスキルに任せる。このスキルが持つのは、段の順番、分け方、着地の型、止まって確認する地点だけ。

境界は、実装の前に決める。

## 再開するとき

1. スライス表と、0で言い直した完了条件を読む(issueか、issueが無ければ会話)。状態が「着地済み」でない最初のスライスが、今のスライス。そのPRがマージされていれば着地済みにし、まだレビューを待っていれば、ブランチの列が埋まっている次のスライスを今のスライスにする。別のセッションで続けていて見つからなければ、前の報告の表と完了条件を利用者に尋ねる。表が無ければ、スライスは1つ
2. そのスライスのブランチと`git log`、review-loopの台帳から、どの段にいるかを決める。台帳は、スライス表の台帳の列(表が無ければ前の報告)にあるディレクトリ。列が空か、そのディレクトリが無ければ(WindowsとWSLはホームが別なので、別の側で再開したときも)、review-loopの0の場所にある、そのブランチの名前で始まる台帳を挙げて、利用者に尋ねる。名前だけで選ばない。同じ名前でも、別の変更の台帳や、放置された台帳があるため。`- 終了:`の行があり、その行のSHAがブランチの先端の祖先で(`git merge-base --is-ancestor <SHA> <ブランチ>`)、その後に足されたのがマージコミットだけ(`git log --no-merges <SHA>..<ブランチ>`が空)なら、レビューは終わっていて、その行がマージを勧めるかを示す。着地の手順が作るマージは、着地の中で検証コマンドを回し直す。SHAが祖先でない(ブランチを巻き戻した)か、マージでないコミットが足されていれば、review-loopを新しく回す。終了の行が無ければ、その台帳のパスをreview-loopに渡して続ける
3. push、PRの作成、issueの更新の前に、GitHubの今の状態を読む。前の実行が途中まで進めていることがある

## 0. 起点を固める

- `gh issue view <N>`で、完了条件、未決事項、blocked byを読む。issueが無ければ、依頼を起点にする。
- 完了条件を、検査できる形に、例を付けて言い直す。入力と期待する結果、回すコマンドと期待する出力を書く。言い直しが依頼と食い違うと思ったら、着手の前に利用者に確かめる。言い直した完了条件は4で使うので、スライス表と同じ場所に残す。issueに書くときは、確認を取ってから書く。
- 次のどれかに当たれば、要件が曖昧とみなして設計議論に入る。
  - 未決事項が残っている
  - 完了条件を、検査できる形に言い直せない
  - 設計の選択肢が開いていて、issueからは選び方が決まらない
- 設計議論は、セッションのモデルをFableにして行う。利用者との対話なので、サブエージェントには任せられない。モデルの切り替えは、アプリのモデル選択で利用者に頼む。`mattpocock-skills:grilling`で詰める。対象の領域に仕様書やADRがあれば、`mattpocock-skills:domain-modeling`も呼ぶ。
- 決まったことは、issueの本文(未決事項、完了条件)に書き戻す。モデルを戻した後は、ここが唯一の引き継ぎ点になる。issueの書き換えは、確認を取ってから行う。
- リポジトリの仕様書が要る変更なら、仕様書を作るか直すことも、完了条件に入れる。

## 1. 分ける

スライスは、単独で検証でき、単独で着地させてよい変更。review-loopは、スライスごとに1回回す。

- 1つのスライスで済むかを決める。済むなら、この段は1行で終える。
- 2つ以上なら、スライス表を作り、承認を1回取ってから、issueに書く。分け方、スライスの型、表の列は`references/slicing.md`にある。issueが無ければ、表を置くissueを作るかを尋ねる。作らないなら、表は会話に書き、スライスを着地させるたびに、今の表と0で言い直した完了条件を報告に載せる。
- 着地の型も、ここで3の表から決める。チームのPRなら、表の承認の後(スライスが1つなら、型を確かめた後)に、`references/team-prs.md`の「スライス表が承認されたら」を進める。
- 境界が見えないときは、使い捨てのspikeで端から端まで通してから分ける。spikeのコードは着地させない。

## 2. スライスごとに進める

1. **実装。** `pstack:poteto-mode`で、実装と検証まで進める。PRの作成と、コミットの並べ替えはここでしない。コミットは関心ごとに分ける。
2. **完了条件の突き合わせ。** スライスの完了条件ごとに、満たしたか、その証拠(テストの名前か、コマンドと結果)を表にする。満たさないものがあれば、直してから進む。
3. **レビュー。** `review-loop`を回す。2で突き合わせた完了条件のコマンドも、review-loopの検証コマンドとして渡す。review-loopの中でツリーが変わっても、最終ゲートが最後のツリーで確かめる。review-loopがマージを勧めずに終わったら(必ず直すものが残る、通せなかった検証がある、高の不変条件が未検証)、着地させずに利用者に戻す。review-loopが台帳を作ったら、そのディレクトリを`~/.local/state/review-loop/<リポジトリ>/<名前>`の形で、スライス表の台帳の列に書く(表が無ければ報告に書く)。issueに載るので、ユーザー名の入った絶対パスにしない。review-loopを回し直したら、新しい台帳のディレクトリに書き換える。
4. **着地。** 下の型で着地させ、スライス表の状態を更新する。状態、ブランチ、台帳の列の更新は、表の承認に含まれるので、確認を取り直さない。

実装の途中で、完了条件に無い変更が要ると分かったとき、スライスを1文で言えなくなったときは止める。検査が通るコミットの境界で切り、残りはスライス表の新しい行にする。番号は振り直さない。後から足す行は、1と同じく承認を取ってから表に書く。review-loopを始めた後は、スライスを割らない。見つかった追加の仕事は、次のスライスにする。

## 3. 着地の型

着地は、スライスの変更がデフォルトブランチ(チームのPRではベースブランチ)に入ること。PRを作っただけでは着地ではない。PRがレビューを待つ間に次のスライスへ進むかは、`references/slicing.md`の「順序と並列」で決める。

型は、プロジェクトの`CLAUDE.md`に書いてあればそれを使う。無ければ、次で決めて利用者に確かめる。

| 型 | 使うとき |
|---|---|
| 直接 | デフォルトブランチへの直接のpushが禁止されておらず、人のレビューも、PRでしか走らない必須の検査も無い |
| PR | 直接のpushが禁止されているか、人のレビューか、PRでしか走らない必須の検査があり、チームの決まりが無い |
| チームのPR | ベースPR、子issue、Sprint、QAの決まりがある。手順は`references/team-prs.md` |

- **直接。** スライスのブランチをデフォルトブランチへ早送りでマージし、確認を取ってpushする。pushが通ったら着地済みにする。早送りできるかは、`git fetch`した後のリモートのデフォルトブランチで決める。早送りできなければ、そのデフォルトブランチをスライスのブランチへマージし、検証コマンドを回し直してから早送りする。pushが拒まれたら、fetchして同じ手順に戻る。
- **PR。** 1つのスライスを1本のPRにする。前のスライスに依存し、前がまだマージされていなければ、前のブランチをbaseにする。依存しなければ、デフォルトブランチをbaseにする。同じheadとbaseの開いたPRが無いことを確かめてから作る。`gh pr list --head`はforkの同じ名前のブランチのPRも返すので、`isCrossRepository`が真のものは除く。マージは、人のレビューがあればその承認を、必須の検査があればその合格を待ち、CIが走るなら緑になってから行う。人の承認を待つ間は見張らず、報告して止まる。積んだPRは、下から順にmerge commitでマージする。上から先にマージすると、変更は下のブランチに入る。squashしたときと、ブランチが自動で消えるときのGitHubの振る舞いは、`split-pr-stack`の「形」にある。下のPRをマージした後、上のPRのbaseがデフォルトブランチに付け替わったかを確かめ、付け替わらなければ`gh pr edit <番号> --base <デフォルトブランチ>`で付け替える。付け替えても、必須の検査が始まらないことがある(baseの変更は`pull_request`の既定の種類に入らない)。そのときは、確認を取って、デフォルトブランチを上のブランチへマージしてpushし、検査を走らせる。
- **PRの本文。** `mattpocock-skills:pr`の型で書き、Summaryの次に、`split-pr-stack/references/templates.md`の子PRの型にある「なぜ要るか」と「なぜこの形か」を、本文の言語で入れる。Evidenceの節には、`bash <review-loopのディレクトリ>/scripts/evidence.sh <台帳のディレクトリ>/evidence.tsv table`の出力を置く。作る前に、同じスクリプトの`check`に台帳の検証コマンドの名前を全部渡し、記録が最後のツリーのものかを確かめる。`table`は今のツリーの記録が無い名前を黙って外すので、表に出た名前だけを渡すと、欠けた検証に気づかない。書いた後の「なぜ」の確かめ方は、`split-pr-stack`の4と同じにする。最後に`prose-polish`にかける。
- **下のスライスを後から直したとき。** 下のブランチを、上のブランチへマージする。rebaseしない。force pushが要らず、レビューで作った指摘ごとのコミットが残る。上のブランチのPRがあれば、マージした後に検証コマンドを回し直し、本文の検証の表(PRの型ではEvidence、チームのPRの子PRでは「動作確認」)を直す。
- push、PRの作成、マージは、確認を取ってから行う。

## 4. 締める

すべてのスライスが着地したら、0で言い直した完了条件を、着地した先のブランチ(デフォルトブランチ、チームのPRではベースブランチ)の先端で1回突き合わせ、結果を報告する。レビューはやり直さない。満たさない条件があれば、承認を取ってスライス表に行を足し、2に戻る。足した行を着地させた後も同じ条件を満たさなければ、止めて利用者に戻す。

issueは、ここで満たしたことを確かめてから閉じる。PRの型では、PRの本文に`Closes`ではなく`Refs #<issue>`を書き、issueは手で閉じる。スライスごとのPRに`Closes`を書くと、1本目のマージで閉じる。直接の型でも手で閉じる。チームのPRでは、ベースPRの`Closes`に任せる。

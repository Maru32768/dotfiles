# タスクの進め方

各段の中身は既存のスキルに任せる。このスキルが持つのは、段の順番、分け方、着地の型、止まって確認する地点だけ。

境界は、実装の前に決める。

## 再開するとき

1. スライス表を読む(issueか、issueが無ければ会話)。状態が「着地済み」でない最初のスライスが、今のスライス。表が無ければ、スライスは1つ
2. そのスライスのブランチと`git log`、review-loopの台帳(パスは利用者に尋ねる)から、どの段にいるかを決める
3. push、PRの作成、issueの更新の前に、GitHubの今の状態を読む。前の実行が途中まで進めていることがある

## 0. 起点を固める

- `gh issue view <N>`で、完了条件、未決事項、blocked byを読む。issueが無ければ、依頼を起点にする。
- 完了条件を、検査できる形に、例を付けて言い直す。入力と期待する結果、回すコマンドと期待する出力を書く。言い直しが依頼と食い違うと思ったら、着手の前に利用者に確かめる。
- 次のどれかに当たれば、要件が曖昧とみなして設計議論に入る。
  - 未決事項が残っている
  - 完了条件を、検査できる形に言い直せない
  - 設計の選択肢が開いていて、issueからは選び方が決まらない
- 設計議論は、セッションのモデルをFableにして行う。利用者との対話なので、サブエージェントには任せられない。モデルの切り替えは、アプリのモデル選択で利用者に頼む。`mattpocock-skills:grilling`で詰める。対象の領域に仕様書やADRがあれば、`mattpocock-skills:domain-modeling`も呼ぶ。
- 決まったことは、issueの本文(未決事項、完了条件)に書き戻す。モデルを戻した後は、ここが唯一の引き継ぎ点になる。issueの書き換えは、確認を取ってから行う。
- リポジトリの仕様書が要る変更なら、仕様書を作るか直すことも、完了条件に入れる。

## 1. 分ける

スライスは、単独で検証でき、単独で着地させてよい変更。1回のship-taskの実行と、1回のreview-loopの単位になる。

- 1つのスライスで済むかを決める。済むなら、この段は1行で終える。
- 2つ以上なら、スライス表を作り、issueに書き、承認を1回取る。分け方、スライスの型、表の列は`references/slicing.md`にある。issueが無ければ、表を置くissueを作るかを尋ねる。作らないなら、表は会話に書き、スライスを着地させるたびに今の表を報告に載せる。
- 境界が見えないときは、使い捨てのspikeで端から端まで通してから分ける。spikeのコードは着地させない。

## 2. スライスごとに進める

1. **実装。** `pstack:poteto-mode`で、実装と検証まで進める。PRの作成と、コミットの並べ替えはここでしない。コミットは関心ごとに分ける。
2. **完了条件の突き合わせ。** スライスの完了条件ごとに、満たしたか、その証拠(テストの名前か、コマンドと結果)を表にする。満たさないものがあれば、直してから進む。
3. **レビュー。** `review-loop`を回す。リスクの区分は、review-loopの0で決める。
4. **着地。** 下の型で着地させ、スライス表の状態を更新する。

実装の途中で、完了条件に無い変更が要ると分かったとき、スライスを1文で言えなくなったときは止める。検査が通るコミットの境界で切り、残りはスライス表の新しい行にする。番号は振り直さない。review-loopを始めた後は、スライスを割らない。見つかった追加の仕事は、次のスライスにする。

## 3. 着地の型

型は、プロジェクトの`CLAUDE.md`に書いてあればそれを使う。無ければ、次で決めて利用者に確かめる。

| 型 | 使うとき |
|---|---|
| 直接 | デフォルトブランチへの直接のpushが禁止されておらず、PRで人がレビューしない |
| PR | PRにCIか人のレビューがあり、チームの決まりが無い |
| チームのPR | ベースPR、子issue、Sprint、QAの決まりがある。手順は`references/team-prs.md` |

- **直接。** スライスのブランチをデフォルトブランチへ早送りでマージする。pushの前に確認を取る。issueは、最後のスライスをpushした後に閉じる。
- **PR。** 1つのスライスを1本のPRにする。前のスライスがまだマージされていなければ、そのブランチをbaseにする。同じheadとbaseの開いたPRが無いことを確かめてから作る。
- **PRの本文。** `mattpocock-skills:pr`の型で書き、Summaryの次に、`split-pr-stack/references/templates.md`の子PRの型にある「なぜ要るか」と「なぜこの形か」を、本文の言語で入れる。「動作確認」は、`bash <review-loopのディレクトリ>/scripts/evidence.sh <台帳のディレクトリ>/evidence.tsv table`で作る。作る前に、同じスクリプトの`check`で、記録が最後のツリーのものかを確かめる。書いたら、この会話の文脈を持たないサブエージェントに本文と差分を渡し、本文で答えていない「なぜ」の問いを挙げさせる。答えはコード、コミット、issueから裏を取って足す。最後に`prose-polish`にかける。
- **下のスライスを後から直したとき。** 下のブランチを、上のブランチへマージする。rebaseしない。force pushが要らず、レビューで作った指摘ごとのコミットが残る。
- push、PRの作成、元のPRを閉じることは、確認を取ってから行う。

## 4. 締める

すべてのスライスが着地したら、0で言い直した完了条件を、着地した先端で1回突き合わせ、結果を報告する。レビューはやり直さない。満たさない条件があれば、スライス表に行を足して2に戻る。

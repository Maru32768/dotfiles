# 週の枠の上限で止まる

大きい仕事が週の枠を使い切ると、利用者のほかの作業が止まる。上限は利用者が`usage-log cap <%>`で決める。このスキルは、仕事の途中で上限と今の消費率を確かめる。上限は仕事の途中でも変わる(リセットの前日に外すなど)ので、確かめるたびに読み直す。

## いつ確かめるか

- 仕事を始める前
- 単位(成果物1つ、ループの1回など)を終えるたび。単位は仕事の指示に従う。指示に無ければ自分で決めて、最初の報告に書く
- サブエージェントをまとめて起こす前。起こした後の分は止められないので、1回に起こす数は、上限までの残りに見合う数にする

確かめるたびに、このスキルをSkillツールで呼び直す。`allowed-tools`の許可は、スキルを呼んだターンの間しか効かない。自動のcompactで、このスキルの本文が文脈から落ちることもある。

## 確かめ方

1. 上限を読む。ホームの`.local/state/usage/weekly-cap`を、絶対パスにしてReadで読む。1〜100の整数(週の枠の%)が1行ある。
   - ファイルが無ければ、上限は無い。2に進まずに続ける
   - 整数として読めないか、ファイルが無いこと以外でReadが失敗したら(確認を断られたなど)、止まって報告する
2. `mcp__ccd_session_mgmt__get_usage`を呼ぶ。遅延ロードのツールなら、先にToolSearch(`select:mcp__ccd_session_mgmt__get_usage`)で読み込む。
   - `plan.status`が`ok`なら、`plan.windows`のうち`label`が`Weekly · all models`のものの`percentUsed`を、週の消費率とする。その枠が無ければ、表示が変わったので、止まって報告する
   - `not_applicable`なら、プランの枠が無い(APIキーなど)ので、続ける
   - `unavailable`なら、`note`が呼び直せば読めると言うときだけ、1回呼び直す。呼び直さないときと、呼び直しても読めないときは、止まって報告する
   - ツールが無ければ(デスクトップアプリの外で動いている)、止まって報告する
   - 上のどれにも当たらなければ(ほかの`status`、`percentUsed`が無い、呼ぶのを断られたなど)、止まって報告する
3. 週の消費率が上限以上なら止まる。未満なら続ける。

## 止まるとき

新しい単位を始めずに止まり、次を報告して終わる。

- 止まった理由(上限に達した、上限のファイルが読めない、`get_usage`で読めない、など)
- 週の消費率と上限、枠がリセットされる時刻(`resetsAt`)。読めなかったものは、読めなかったと書く
- 終えた単位と、再開するときに始める単位
- 再開の方法。上限に達したなら、`usage-log cap off`で上限を外すか、`usage-log cap <%>`で上げるか、リセットを待つ。読めずに止まったなら、その原因(Readの確認を断った、`get_usage`が一時的に読めない、デスクトップアプリの外で動いている、など)を直してから再開する。どれにするかは利用者が決める

上限のファイルは読むだけにする。外したり上げたりは、このスキルからはしない。

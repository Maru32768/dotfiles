# humanizer ルールをかける

## 入力

- **対象:** ファイルと、直してよい行範囲。base を渡されたら、`<base>...HEAD` で追加・変更された段落だけを対象にする（新規ファイルは全体）。差分に無い既存の文は直さない。PR/MR 本文は、GitLab なら `glab mr view -F json --jq .description`、GitHub なら `gh pr view --json body --jq .body` で取る。
- **言語:** ファイルごとに、地の文の言語で `ja` か `en` を決める。
- **作業ディレクトリ `<work>`:** 呼び出し元が渡す（prose-polish ならその `<work>`）。渡されなければ、システムプロンプトにscratchpadのディレクトリが書かれていればその下に、無ければ`/tmp`の下に、`imos-humanizer-<対象の名前>/`を作る。WindowsのGit Bashでは、`cygpath -m`で`C:/...`の形に直したパスを使う。
- **原文の退避と入力稿:** 呼び出し元が渡す（prose-polish なら `<path>.orig` と `<path>.h0`）。単独で使うときは、原文を `<work>/<path>.orig`（PR/MR 本文は `pr-body.orig.md`）に置き、同じものを `<path>.h0`（`pr-body.h0.md`）にコピーする。
- **文書の種類と読者:** 呼び出し元が渡す。単独で使うときは、文書から決める。
- **検査:** 呼び出し元が渡せばそれを使う。単独で使うときは、日本語は下の yomiyasu の検査、英語は無し（親の diff がその代わり）。
- **文書の規約:** リポジトリの `CLAUDE.md` などに文書の決まり（訳を行ごとに対応させる、表記の規則など）があれば、サブエージェントに制約として渡す。ルールより優先する。訳と行ごとに対応させている文書では、行を分けたりつないだりさせず、見出し・箇条書き・空行の位置も変えさせない。

対象にするのは地の文だけ。コード、コードコメント、コードブロック、インラインコード、URL、識別子は残す。`CLAUDE.md` `AGENTS.md` `SKILL.md` などエージェントへの指示ファイルも対象外にする。

## 手順

1. **ルールを取る。** 使う言語の分だけ取る。

   ```bash
   bash ~/.claude/skills/imos-humanizer/scripts/fetch-rules.sh <ja|en> <work>/humanizer.<ja|en>.txt
   ```

   ルールの本文はライセンスが分からないので、dotfiles には sha256 だけを固定している（`rules.sha256`）。上流が更新されて一致しないと、このスクリプトは失敗する。そのときは 2 以降を飛ばし、「humanizer ルールが固定した版と違うので飛ばした。`fetch-rules.sh --check` で差分を見て `rules.sha256` を更新する」と報告する。サブエージェントには URL ではなく取得したパスを渡し、Read で読ませる。WebFetch は長いページを要約して返すので、ルールの後半が落ちる。

2. **ルールをパスごとに新しいサブエージェントでかける。** パス N では、まだ収束していないファイル1つにつきサブエージェントを1つ、同じメッセージで並列に起動する。worktree は要らない。本体ツリーには書かせない。前のパスのサブエージェントを再開しない。自分で書いた直後の文は直す所が見えにくく、収束の合図（「変更なし」）も甘くなる。プロンプトに以下を書く。
   - `<work>/humanizer.<ja|en>.txt` を Read で最後まで読め。そのうえで入力をルールに完全に適合するよう、隅々まで何度も確認して修正しろ。
   - 入力は前の段の出力 `<path>.h<N-1>`。原文の退避のパス、直してよい行範囲、文書の種類と読者も渡す。
   - 次の制約はルールより優先する（ルールの「編集禁止範囲」として扱え）。
     - 範囲外の行、コードブロック、インラインコード、URL、識別子、PR/MR 本文のテンプレート由来の見出しと節の並びを変えるな。
     - **事実・例・手順・補足を足すな。** ルールは具体例や手順の補足を促すが、足りないと思ったら報告に回せ。docs に足された説明は誰も検証しない。
     - 主張・条件・確度を変えるな。**弱める方向も含む**（言い切りを「〜ことがある」や "may" にする等）。実装と食い違う記述を見つけても直さず報告しろ。
     - 表記（日本語なら長音・送り仮名・カタカナと英字の選び方、英語なら綴りの米英・大文字の使い方）は文書とリポジトリの既存の表記に合わせ、ルールの表記の規定では変えるな。差分の段落だけ表記が変わると、文書の中で揺れる。
     - 文書の規約があれば、それも書く。
   - 採用した変更が0件なら、ファイルを書かずに「変更なし」と報告しろ。
   - 変更があれば `<path>.h<N>`（PR/MR 本文は `pr-body.h<N>.md`）に書き、検査を通せ。`--source` は前のパスの出力ではなく**推敲前の退避**を渡す。パスごとの小さなずれの積み重ねを、原文との比較で捕まえるため。このパスで変えていない行の指摘は前の段で扱い済みなので無視してよい。日本語の検査は、`<work>`で実行し、ファイルは`<work>`からの相対パスで渡す。yomiyasuは、実行したディレクトリの外のファイルと、そこからの道筋に点で始まる部分があるパスを読まずに、終了コード2で止まる。語の一覧は`<work>`から上のgitのリポジトリの`.yomiyasu-words/`しか探さないので、対象のリポジトリの最上位に`.yomiyasu-words/`があれば、`--words <その絶対パス>`を足す。

     ```bash
     cd <work> && python3 ~/.claude/skills/yomiyasu/scripts/yomiyasu_check.py run \
       --source <退避した原文> --final <推敲稿> --doc-type <種類> --reader expert \
       --fail-on meaning-risk --fact-gaps --state-dir .yomiyasu
     cd <work> && python3 ~/.claude/skills/yomiyasu/scripts/yomiyasu_check.py verify \
       --final <推敲稿> --state-dir .yomiyasu
     ```

     `--doc-type` は、PR/MR 本文が `pr`、手順書・README が `manual`、設計書・仕様書が `formal`。当てはまらなければ指定しない。`--state-dir`を省くと、`<work>`より上にgitのリポジトリがあれば、その直下に`.yomiyasu/`が作られる。終了コード1（meaning-risk）が出たら、その書き換えを戻すか、意味が同じだと言える根拠を報告しろ。
   - 推敲稿には注記や質問を入れるな。報告は本文で返せ。採用した変更（5点まで）、ルールに照らして気づいたが制約で採らなかったもの、書き手に確かめたい点、検査の指摘とその扱い。

3. **親がファイルごとに収束を判定する。**

   ```
   「変更なし」                     →  収束。直前の段の出力を採る
   前のパスの変更を戻しているだけ    →  収束扱い。戻した方（原文に近い方）を採る
   それ以外                         →  次のパスへ
   ```

   **上限3パス。** 3パス目でも変更が出たら `.h3` を採り、「未収束」と報告する。回数は文章量で決めない。ルール自身が「再確認で新しい問題が見つからなければ完了」と定めているので、長い文書はパスが自然に増え、短い文書は1パスで止まる。上限の3は記事が全例でかけた回数で、それより多い回数で良くなるという根拠は無い。一方でパスを重ねるほど小さな意味のずれが積み重なり、しかも yomiyasu の meaning-risk は確度を弱めた書き換えを数えない。英語には意味の検査が無いので、親の diff がその代わりになる。

   採った出力を `<work>/<path>.final`（PR/MR 本文は `pr-body.final.md`）にコピーする。

4. **単独で使ったときは、親が反映する。** 呼び出し元があれば、反映は呼び出し元に任せて 5 に進む。サブエージェントの推敲を鵜呑みにしない。
   - `diff -u <orig> <final>` を自分で読む。範囲外の行の変化、コードブロック・識別子・数値・リンクの変化は戻す。
   - 主張・条件・確度が動いたものは採らない。確度は弱まった方向も見る。原文に無い説明・例・手順が足されていたら戻す。
   - 「書き手に確かめたい点」は、コードか会話から答えが出るものは親が答えて反映する。出ないものは報告に回す。
   - ドキュメントは本体ツリーに反映する。コミットはユーザーの指示を待つ。
   - PR/MR 本文は `glab mr update <id> --description "$(cat pr-body.final.md)"`（GitHub は `gh pr edit <n> --body-file pr-body.final.md`）で更新し、**取得し直して最終稿と一致するか確認する。** 元に戻すときは `pr-body.orig.md` を同じ手順で書き戻す。

5. **報告する。**
   - ファイルごとに何パスかけて収束したか（未収束で上限に達したもの、ルールが固定した版と違って飛ばしたものはそう書く）と、採った出力のパス
   - 制約で採らなかった変更、書き手に確かめたい点、検査の指摘とその扱い
   - 単独で使ったときは、反映したファイル、PR/MR 本文を更新したか、採らなかった変更、元の本文の控え `pr-body.orig.md` のパス

   `<work>` は PR/MR 本文の控えがあるので消さない。

## ルールの更新

上流が更新されると 1 で止まる。差分を読んでから、dotfiles の `home/dot_claude/skills/imos-humanizer/rules.sha256` を書き換える。

```bash
bash ~/.claude/skills/imos-humanizer/scripts/fetch-rules.sh --check
```

差分は、前に照合した版の控え（`~/.cache/imos-humanizer/`）と比べる。控えが無い端末では差分を出せないので、控えのある端末で確かめる。

## 失敗モード

| 症状 | 原因 | 対処 |
|---|---|---|
| パスが終わらない | 言い換えが次の言い換えを呼ぶ | 「変更なし」か前のパスを戻すだけなら収束扱い、上限3パス |
| docs に検証していない説明が増える | ルールが具体例や手順の補足を促す | 足すなと指示し、足された行は親が戻す |
| 言い切りが「〜ことがある」や "may" に弱まる | 確度を弱めた書き換えは yomiyasu の meaning-risk に数えられない | 親が `.orig` との diff で確度を見る |
| パスごとに意味が少しずつずれる | 検査の `--source` に前のパスの出力を渡した | `--source` には推敲前の退避を渡す |
| ルールの後半が効いていない | WebFetch が長いページを要約した | 取得したファイルを Read で読ませる |

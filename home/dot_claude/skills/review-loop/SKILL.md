# レビューループ

実装が一通り終わった差分を、**片づけ、独立したレビュー、再現、修正、修正の確認**の順に通す。レビューが始まった後にツリーを変えるのは、再現できた指摘への修正だけにする。単純化や推敲をレビューの後に置くと、そこで入った退行を誰も見ない。

優先順位は、重要な欠陥の検出、誤検知による有害な修正の回避、費用の順。指摘が0件でも、正しさの証明ではない。何を見て、何を実行で確かめ、何を未検証で残したかを分けて報告する。

モデル: ラウンドのレビュアーと1のサブエージェントはOpus(Agentツールに`model: "opus"`)。別レビューはFable(`model: "fable"`)とCodex(`gpt-6-astra`)。effortは指定しない。

## 流れと停止条件

| 段 | 軽 | 通常 | 高 |
|---|---|---|---|
| 前提を固める(0) | する | する | する。不変条件を台帳に書く |
| 片づけ(1) | 推敲だけ | する | する |
| R1(2) | correctnessだけ | 2トラック | 2トラック |
| 再現して修正する(3) | する | する | する |
| R2(4) | 飛ばす | 修正の差分を見る | 全体を見る |
| R3(4) | 飛ばす | R2で必ず直すものが出たときだけ | 同じ |
| FableとCodex(5) | 飛ばす | する | する |
| 最終ゲート(6) | する | する | する |

- 「必ず直すもの」は3で決める。
- ラウンドは3回まで。R3でも必ず直すものが出たら、直さずに止めて、設計の前提を利用者に戻す。止めたときは、5と6を飛ばして報告する。
- 必ず直すものが残るとき、高の不変条件が未検証のときは、安全だと報告しない。マージを勧めない理由と、要る判断を書く。
- 段に入るたびに、この文書のその段と台帳を読み直す。長い実行では、前に読んだ内容が文脈から落ちる。

## 0. 前提を固める

- **対象。** `git log --oneline <base>..HEAD`でコミットを並べ、baseをSHAで固定する。積んだブランチなら、baseは直接の分岐元にする。開始時のHEADも控える。未コミットの変更は、先にコミットするか、対象から外すかを決める。サブエージェントには、`master`との差分ではなく、このSHAの範囲を渡す。
- **検証コマンド。** プロジェクトの`CLAUDE.md`、`README`、`package.json`、`Makefile`から、型チェック、lint、テストのコマンドを拾い、台帳に書く。回すときは`bash <このスキルのディレクトリ>/scripts/evidence.sh <台帳のディレクトリ>/evidence.tsv run <名前> -- <コマンド>`を使う。終了コードと、そのときの作業ツリーの指紋が記録される。手元で通らないコマンドは、分かった時点で、代わりのコマンドと一緒に台帳に書く。
- **意図とリスク。** PR/MR本文、issue、設計資料、テストから、何を実現する変更か、何を壊してはいけないかを台帳に書く。実装から推測した仕様は、仮説と書く。リスクは次の3つから選び、理由を台帳に書く。行数では決めない。迷ったら通常にする。
  - 軽: 文書、設定値、機械的な改名、テストだけの変更
  - 通常: 軽にも高にも当たらないもの
  - 高: 認可、権限、隔離、秘密情報、永続化と移行、並行と冪等とリトライ、公開APIの互換性、CI/CD、信頼できない入力の解釈、取り消せない外部への作用。検証できる不変条件(例: 同じイベントを再配送しても二重に更新しない)を台帳に書く。認可や秘密情報に触れるなら、専用のセキュリティレビュー(`/security-review`など)を足す
- **台帳。** 台帳のディレクトリを作る。場所は、システムプロンプトにscratchpadのディレクトリが書かれていれば`<scratchpad>/review-loop/<名前>/`、無ければ`/tmp/review-loop/<名前>/`にする。WindowsのGit Bashでは、`cygpath -m`で`C:/...`の形に直したパスを使う。`/tmp/...`のままだと、ReadやWriteは別の場所を指す。`<名前>`は、ブランチ名の`/`を`-`に替えたもの。ブランチが無ければ(detached HEAD)、開始時のHEADの短いSHAにする。同じ名前のディレクトリが既にあれば、中断した同じレビューを続けるときだけそれを使う。それ以外は、名前の末尾に`-2`のように番号を足して新しく作る。scratchpadはセッションごとに別の場所なので、別のセッションで続けるときは、前の台帳の絶対パスを利用者に尋ねる。分からなければ、新しく作る。その中に`ledger.md`を作り、絶対パスを利用者に伝える。型と行の印は`references/ledger.md`にある。ラウンドごとにプロンプトへ手で書き写さず、絶対パスを渡す。

## 1. 片づける(ツリーを変える作業はここまで)

軽では、4の推敲だけを行う。

1. サブエージェントに`ponytail:ponytail-review`スキルを実行させ、過剰な実装だけを`file:L<行>: <tag> <削るもの>. <代わり>.`の形で挙げさせる。適用はさせない。
2. 採る候補を決め、サブエージェントに`simplify`スキルを実行させて適用させる。1の出力と、次の制約を渡す。採らない候補は、理由と一緒に台帳の「見送り」に書く。

   ```
   次は意図的な設計なので、元に戻すな:
   - <制約と、それが要る理由>
   テストを消すな。テストを消す提案は、そのテストだけが落とす変異が無いかを先に確かめろ。
   既存のテストを変えるなら、公開仕様を確かめているテストの期待値は書き換えるな。
   行数が減っても読みにくくなったものは戻せ。コミットはするな。
   ```

3. 適用の後、親が差分を読み、候補ごとにコミットする。「コメントの整理だけ」と報告されても、振る舞いの変更が紛れていないかを見る。
4. `<base>...HEAD`で変わった文書に`prose-polish`の対象があれば、`prose-polish`スキルを実行する。base、作業ディレクトリ(台帳のディレクトリの`prose/`)、台帳のパスを渡す。PR/MRがあれば、本文も渡す。採らなかった変更は、台帳の「推敲で採らなかった変更」に書かせる。反映した文書は、親が差分を読み、検証コマンドを通してからコミットする。
5. 検証コマンドを全部通す。

## 2. R1

2トラックを、同じメッセージで同時に起こす。軽ではcorrectnessだけにする。

| トラック | 見るもの |
|---|---|
| correctness | 実装の誤り、設計や仕様との不整合、データの流れ、影響先。1で推敲した文書があれば、`prose/`の`.orig`と`.final`を比べ、主張、条件、確度、手順が変わっていないか |
| テスト品質 | 何も確かめていないテスト、モックを確かめているだけのテスト、重要な仕様の未検証。選んだmutationと不変条件の検証。手順は`references/mutation.md`を読ませる |

どちらのレビュアーにも、次を書く。

- `isolation: "worktree"`で起こす。worktreeはリモートのデフォルトブランチから作られるので、冒頭で`git rev-parse HEAD`と`git status --short`を確かめさせ、自分専用のworktreeで守るべき変更が無いときだけ、対象のSHAへ`git reset --hard`させる
- 対象のコミットの範囲(SHA)。`master`とdiffしない
- 台帳の絶対パス。「対応済み」「見送り」「却下」にあるものは、新しい論拠が無い限り出し直さない
- プロジェクトの規約(`CLAUDE.md`など)を先に読む
- 依存パッケージが要るなら、存在とロックファイルとの一致を確かめてから入れる。ビルドとテストの並列数に上限があれば守り、資源の不足をコードの失敗と扱わない
- 重大度をMust、Should、Couldで付ける。`file:line`、故障条件、期待と実際の差、根拠(実行の結果か、仕様の不変条件)を書く
- 指摘ごとに、実証済み、静的に根拠あり、未検証、反証済みのどれかを書く。実行していない推測を「再現済み」と書かない。差分より前からある問題は、既存問題と書き、今回の変更で悪化するか露呈するかを説明する
- 指摘ごとに、同じ型の問題がほかに無いかを、依存先と呼び出し元まで探す
- Mustが0件、Shouldが0件なら、そう書く
- 内部でサブエージェントを起こしたら、結果を待ってまとめてから報告する。最終報告は本文で返す
- 修正を適用しない

差分がキャッシュやメモ化(`WeakMap`、`Map`、`??=`などで結果を持ち回すもの)を持ち込んでいたら、テスト品質のレビュアーに`references/caching.md`も読ませ、親もそれに従う。

## 3. 再現して修正する

- **直す前に、親が自分で再現する。** MustとShouldは、最小の再現を書いて動かす、経路をgrepして追うなどして、確かめてから直す。反証できたものだけを、理由と一緒に「却下」に書く。再現できないものは、前提が誤っているのか、条件が足りないのか、環境が使えないのかを分け、後の2つは「未検証」として残す。
- **必ず直すもの。** 利用者に見える誤動作、データや秘密の損失、常に通ってしまう検査、仕様や完了条件の未充足。テストの穴は、0で書いた不変条件か、テスト品質のレビュアーが挙げた「見逃すと問題になる振る舞い」を守るものだけを直す。それ以外の指摘は、理由と一緒に「見送り」に書いて直さない。1行で閉じて振る舞いを変えないものは、拾ってよい。
- **同じ型を先に探す。** 指摘が正しいと分かったら、同じ型の欠陥がほかに無いかを探してから直す。
- **指摘ごとに1コミット。** 修正する、影響するテストを通す、コミットする、台帳の「対応済み」にコミットを書く、の順。同じ原因の指摘は1コミットにまとめてよい。件名には直した内容を書き、ラウンドの番号や「レビュー指摘対応」は書かない。
- **直ったことを確かめる。** 同じ再現の手順で、直す前と後を比べる。mutation由来の指摘は、同じパッチを`evidence.sh`の`mutate`で当て直し、`Killed`になることを確かめる。
- **文書とコメントの修正も裏を取る。** 「〜にはXを使え」「〜も対象」と書き足すときは、そのXと対象を実際に動かして確かめる。
- **修正でテストやCIを変えたら、** 消したテスト、緩めた期待値、skipを、理由と一緒に台帳に書く。
- **書き込むのは親だけ。** レビュアーは自分のworktreeの中だけを書き換える。修正のエージェントを並列に走らせない。
- ラウンドの修正が揃ったら、検証コマンドを全部通す。各ラウンドの入力のSHAと修正後のSHAを、台帳に書く。

## 4. 修正を確かめる(R2、R3)

軽では飛ばす。

- R2は、R1の修正(レビュー入力のSHAから修正後のSHAまで)とその影響先を、2トラックで見る。差分の行だけでなく、その行が影響する箇所も読ませる。高では、`<base>...HEAD`の全体を見る。修正が無ければ飛ばす。修正が文書とコメントだけなら、correctnessだけにする。
- R3は、R2で必ず直すものが出たときだけ回す。範囲は、R2の修正とその影響先。
- R2とR3のレビュアーへの指示に、新しい種類の欠陥が見つかったとき、影響先が広いとき、前のレビューの前提が崩れたときは、範囲を`<base>...HEAD`の全体に広げる、と書く。レビュアーはその回の中で広げ、親は広げるために回を足さない。
- R3でも必ず直すものが出たら、直さずに止める。同じ種類の欠陥が続いているのか、別の層へ波及しているのかを指摘の中身で見分け、設計の前提、範囲、欠陥の種類を利用者に戻す。

## 5. 収束したらFableとCodexに1回ずつ読ませる

軽では飛ばす。Opusのラウンドが終わった後に、別のモデルに1回ずつ読ませる。同じメッセージで同時に起こす。

- Fable: Agentツールに`model: "fable"`を渡し、`<base>...HEAD`の全体を読ませる。2のレビュアーと同じく`isolation: "worktree"`で起こし、修正は適用させない
- Codex: Bashで、バックグラウンドで実行する。数分かかる

```bash
git status --short            # 未コミットの変更があれば先にコミットする
codex review --base <base> -c model=gpt-6-astra -c review_model=gpt-6-astra -c model_reasoning_effort=high   # <base>は0で固定したSHA
```

Codexはレビューのモデルを`review_model`から先に決めるので、設定ファイルに`review_model`があると、`model`だけでは別のモデルが読む。

- Fableに渡すのは、差分と変更の意図だけにする。台帳やここまでの結論は渡さない。Codexにもプロンプトを足さない。同じ前提に引きずられると、別のモデルに読ませる意味がなくなる
- 指摘は3と同じに扱う
- 直したら、その修正の差分と影響先を、Opusの2トラックで1回だけ確かめる。FableとCodexはもう呼ばない。その確認で必ず直すものが出たら、直して、同じ再現の手順で確かめ、報告に書く。レビューの回はもう足さない
- `codex`が無いとき、ログインしていないときは、Codexだけ飛ばし、最終報告に理由を書く

## 6. 最終ゲート

- `bash <このスキルのディレクトリ>/scripts/evidence.sh <台帳のディレクトリ>/evidence.tsv check <名前...>`で、検証コマンドが全部、最後のツリーで通っていることを確かめる。`STALE`と`MISSING`は回し直す。回し直しても`STALE`のままなら、そのコマンドが、無視されないファイルを実行のたびに違う中身で書き換えている。書き出す先を無視される場所に移すか、そのファイルを`.gitignore`に足してから回し直す。回し直しても`FAILED`のものは、3の手順で直し、その修正の差分をcorrectnessで1回確かめてから、このゲートをやり直す。この確認で必ず直すものが出たら、5の後の確認と同じく、直して同じ再現の手順で確かめ、報告に書く。レビューの回は足さない。台帳の工程の印は`final-correctness`にする。ゲートのやり直しは1回までで、それでも通らないものと直せないものは、報告の「通せなかった検証」に書き、マージを勧めない。
- `git diff --stat <開始時のHEAD>..HEAD -- <テストとCIのパス>`で、ループの中で変えたテストとCIを一覧にし、台帳の記録(消したテスト、緩めた期待値、skip)と合うかを確かめる。
- PR/MRがあれば、本文が最後の差分と合っているかを確かめる。「確認したこと」は、同じスクリプトの`table`の出力から書く。本文を直したら、`prose-polish`にかける。PR/MRが無ければ、最終報告にそう書く。

## 報告

- リスクの区分と理由、各ラウンドの範囲、MustとShouldの件数
- 重要な指摘ごとの、故障条件、根拠(実行、静的、未検証)、直した後の確認
- mutationで選んだ範囲、結果、省いた範囲。不変条件のうち、検証したものと未検証のもの
- 自分の修正が入れた退行(隠さずに書く)
- 見送った項目と理由。台帳の「申し送り」は独立した項にする
- FableとCodexの指摘の件数と扱い。Codexを飛ばしたなら理由
- 通せなかった検証コマンドと、未検証のまま残っているもの
- R3で止めたなら、残った指摘と、収束しない理由
- prose-polishの報告
- 台帳のディレクトリの絶対パス

後片付け: レビュー用のworktreeとブランチを消し、作業ツリーをきれいにして終える。台帳のディレクトリは消さない。

規則の元になった実績と参考資料は`references/background.md`にある。実行のたびに読む必要は無い。

# レビューループ

実装が一通り終わった差分について、**独立したレビュー → 証拠の検証 → 修正 → 再検証**を繰り返す手順。

単発レビューとの違いは、**2トラック並列**（correctness / テスト品質）、**選択的な mutation・性質の検証**、**停止条件と残存リスクの明示**。Must/Should が0件になっても正しさの証明ではない。レビューが何を見たか、何を実際に検証したか、何を未検証のまま残したかを区別する。

優先順位は **重要なバグの検出 > 誤検知による有害な修正の回避 > ラウンド数・実行コストの削減**。スタイルや好みの議論でループを増やさない。

**モデル:** ラウンドのレビュアー、4 と 5 のサブエージェントは Opus で起動する（Agent ツールに `model: "opus"`）。Fable と Codex は、収束の後に1回ずつだけ読ませる（3 の最後）。毎ラウンド上位のモデルを回すとトークンがかさむため。effort はどれも指定せず、セッションに合わせる。

## 0. 前提の確定（ここを飛ばすと全部無駄になる）

ループを始める前に、親（＝このスキルを実行しているあなた）が以下を確定させる。

### ベース ref を1回だけ計算して固定する

```bash
git log --oneline <base>..HEAD   # レビュー対象のコミットを列挙
```

- スタックした MR / 派生ブランチなら、`master` ではなく**直接の分岐元**が base。
- 確定したら「対象は `<base>...HEAD` の N コミット（ハッシュを列挙）」と書き、**サブエージェントに `master` との diff を禁止する**と明記する。

> 実績: これを省いた初回、レビュアーが `master...HEAD`（16コミット/66ファイル）を見て、3件中2件が範囲外の指摘になった。

`base` はコミットSHAとして固定し、開始時の `HEAD` も記録する。ラウンドを進めるたびに対象 `HEAD` を更新し、**その時点の `base...HEAD` がレビュー対象全体**であることを明記する。未コミットの変更があれば対象に含めるか先にコミットするか決め、取りこぼさない。各ラウンドの**レビュー時のHEAD（入力）**と**修正後のHEAD（出力）**を別々に台帳へ記録する。R3以降の差分限定レビューでは、直前ラウンドの入力SHAから出力SHAまでを比較する（出力SHA同士を比較すると修正差分が空になる）。

### 検証コマンドを特定する

プロジェクトの `CLAUDE.md` / `README` / `package.json` / `Makefile` から、型チェック・lint・各テストスイートのコマンドを拾って控えておく。サブエージェントにもこの一覧を渡す。

**手元で通らないコマンドは、通らないと分かった時点で台帳に書く。** ローカル固有の前提（DBエミュレータが要る等）が満たせない場合、代替コマンド（パス指定で該当スイートだけ回す等）まで書いておく。書かないと**全レビュアーが同じ壁に各10分ずつ溶かす。**

> 実績: Docker が落ちていて DB エミュレータが無く、backend のテスト全体が
> 610秒後にテストランナーの panic で落ちた。ドメイン層だけを回すコマンドを台帳に書いてからは誰も踏まなくなった。
> このとき**「全件は未検証」は最終報告に必ず書く。** 通ったことにしない。

### 変更の意図・リスク・検証対象の性質を確定する

PR/MR本文、Issue、設計資料、テスト、既存実装から「何を実現する変更か」「何を壊してはいけないか」を整理する。**実装から推測した仕様は仮説として明記**し、未確認の期待動作を断定しない。

| 区分 | 目安 | レビュー方針 |
|---|---|---|
| 通常 | 局所的な表示・変換・非クリティカルなロジック | 2トラック + 代表的な mutation。性質が明確なら property-based testing |
| 高リスク | 認可・機密情報・決済・DB整合性・マイグレーション・並行処理・冪等性・リトライ・CI/CD・公開API互換性・障害時の復旧 | 2トラック + 明示した不変条件/故障モデルを重点検証。必要なら専用の安全性・セキュリティレビュー |

**行数だけでリスクを決めない。** 変更前後の振る舞い、影響範囲、不可逆性、ロールバック可否を考える。高リスクと判断した理由、検証可能な不変条件（例: 同一イベントを再配送しても二重更新しない）、必要な検証方法を台帳に書く。性質が確定できない場合は「仕様未確定」として報告対象にする。

このSKILLはどちらも2トラックを維持する。低リスク変更でこの手順自体が過剰なら、ユーザーが単発レビューを求めている場合に限り `code-review` を使う。

### 台帳ファイルを作る

台帳のディレクトリを作る。場所は、システムプロンプトにscratchpadのディレクトリが書かれていれば`<scratchpad>/review-loop/<名前>/`、無ければ`/tmp/review-loop/<名前>/`にする。WindowsのGit Bashでは、`cygpath -m`で`C:/...`の形に直したパスを使う。`/tmp/...`のままだと、ReadやWriteは別の場所を指す。`<名前>`は、ブランチ名の`/`を`-`に替えたもの。ブランチが無ければ(detached HEAD)、HEADの短いSHAにする。リポジトリの`.git`や`.claude`の下には置かない。どちらもClaude Codeの保護パスで、権限のモードによっては、書き込みに確認が出るか、拒否される。同じ名前のディレクトリが既にあれば、中断した同じレビューを続けるときだけそれを使う。それ以外は、名前の末尾に`-2`のように番号を足して新しく作る。

その中に`ledger.md`を作り、以下を追記していく。**ラウンドごとにプロンプトへ手で書き写さない。絶対パスを渡す。**

```markdown
# 対応済み
- [R1/Must] <内容> → <どう直したか>（<直したコミット>）

# 意図的に見送り（再提起禁止・新しい論拠がある場合のみ可）
- <内容> → <理由>

# 申し送り（本 MR の範囲外。別 MR で判断が要る）
- <内容> → <なぜこの MR に入れないか>

# 却下した指摘（前提が誤っていたもの）
- <内容> → <何が誤りだったか>

# 推敲で採らなかった変更
- <ファイル or PR 本文> <推敲案> → <採らなかった理由（意味が動いた・範囲外 等）>

# 対象とリスク
- base SHA / 初回 HEAD SHA / 現在の HEAD SHA / 各ラウンドのレビュー入力SHAと修正後SHA
- 変更の意図 / リスク区分と理由 / 不変条件とその根拠（仕様 or 仮説）

# 指摘と検証証拠
- [R1/Should] <種類・file:line・影響条件> → <実証済み/静的に根拠あり/未検証/反証済み>、<再現コマンドや仕様の根拠>、<結果>

# mutation・性質の検証
- <対象・選定理由・実行したテスト・Killed/Survived/NoCoverage/Timeout/Invalid/Equivalent疑い・結論>
- <検証を省略した範囲と理由> / <性質・故障モデルと結果>

# 対応済みラウンドの範囲
- R<N>: <レビュー入力SHA → 修正後SHA>、<base...HEAD全体／入力SHA..出力SHAと影響先のどちらを見たか>

# 環境の注意・未検証
- <通らない検証コマンドと、その代替、影響を受ける機能>

## R<N> の検証結果
- <コマンド> → <成功/失敗/未実行>、<対象と件数>、<所要時間（取得できる場合）>
```

「意図的に見送り」と「申し送り」は分ける。前者はレビュアーへの再提起禁止リスト、後者は**ユーザーへの報告対象**で、最終報告に必ず載せる。混ぜると仕様レベルの発見が見送り欄に埋もれる。

台帳の「未検証」は「誤りなので却下」とは違う。環境不備や仕様不明による未検証の指摘を、再現できなかったという理由だけで消さない。

### 指摘を1件1行で記録する

台帳と同じディレクトリに`findings.tsv`を作る。レビュアー、4と5の工程、親自身が見つけた欠陥と提案を、直さなかったものも含めて、親が足す。1行は1つの欠陥で、1つの修正で消えるものは1行にまとめる。扱いを決めたときに足し、直したら`commit`を埋め、後で扱いが変わったら行を書き換える。どの工程が何を見つけたかを後で数えるための記録で、台帳の文章の代わりにはしない。1行目は次の見出しにする。値の無い列は`-`にする。

```
id	source	also	severity	kind	origin	file	summary	outcome	commit
```

- `id`: 1からの連番
- `source`: その欠陥を最初に出した工程。`R1-correctness`、`R1-test`(R2以降も同じ形)、`fable`、`codex`、`followup-correctness`、`followup-test`(FableとCodexの指摘を直した後の差分ラウンド)、`ponytail`、`simplify`、`prose`、`final`、`parent`(親が自分で見つけた)。同じラウンドのcorrectnessとtestがどちらも出したら、correctnessにする
- `also`: 同じ欠陥を出した、ほかの工程。`source`と同じ書き方で、複数あれば`,`で並べる
- `severity`: 親が扱いを決めたときの`Must`、`Should`、`Could`。提案は`-`
- `kind`: `code`(実行されるコードと設定)、`test`、`docs`(文書、コメント、PR/MR本文、エージェントへの指示文)、`suggestion`(欠陥ではない削除、単純化、言い換えの提案)
- `origin`: `start`(レビュー対象の差分が持ち込んだ)、`fix`(ループの中の修正、単純化、推敲が持ち込んだ)、`pre-existing`(差分より前からある)。修正コミットが変えた行から出た欠陥は`fix`にする
- `file`は`path:line`、`summary`は1行の説明で、タブと改行を入れない
- `outcome`: `fixed`(直した、提案を採った)、`rejected`(反証した)、`deferred`(見送った、提案を採らなかった)、`handoff`(申し送り)、`unverified`
- `commit`: 直したコミット。複数あれば`,`で並べる
- 4の工程は、提案1件を1行にする。ponytail-reviewの提案をsimplifyが適用したものは、`ponytail`の行にだけ書く

## 1. 1ラウンド = 2トラック並列

**必ず同じメッセージで2つ同時に**起動する。片方ずつ回すと倍の時間がかかるうえ、観点が混ざる。

| トラック | 見るもの |
|---|---|
| correctness | 実装の誤り、設計・仕様との不整合、データフロー、影響先、前ラウンドの修正が壊したもの |
| テスト品質 | vacuous なテスト、モックを検証しているだけのテスト、重要な仕様の未検証、選択的な mutation と不変条件の検証 |

### 両トラック共通で必ず書くこと

- **`isolation: "worktree"` を指定する。** レビュアーは mutation でファイルを書き換えるため、本体ツリーと分離しないと親の編集と衝突する。
- **worktree の HEAD が対象コミットとは限らない。** 冒頭で `git rev-parse HEAD` と `git status --short` を確認させる。**自分専用のscratch worktreeで、保護すべき変更がないことを確認できたときだけ**対象SHAへ `git reset --hard` する。共有worktreeやユーザーの変更に対してresetしない。
- **worktree には `node_modules` が無い場合がある。** 存在と依存関係を確認してから必要なら `pnpm install --frozen-lockfile`（等）を実行する。書かないと「テストが動かない」で1往復潰れる。worktree が本体のディレクトリの下にあると、親の `node_modules` に解決されて古い依存のまま動いてしまうので、動くかどうかではなく存在とロックファイルとの一致で確かめさせる。
- **ビルドとテストの並列数の上限を書く。** 2トラックはそれぞれの worktree で同時にビルドとテストを回し、親の作業とも重なる。プロジェクトの規約やメモリに上限（ビルドのジョブ数、E2E のワーカー数など）があれば、その値を書き、資源不足のエラーをコードの失敗として扱わないよう伝える。
- 対象コミット範囲（ハッシュ列挙）と「`master` と diff するな」。**未コミットの変更は別worktreeに自動では反映されない**。含めるなら親が安全にsnapshot/commitする。
- 台帳ファイルのパスと「ここに載っているものは新しい論拠が無い限り再提起するな」
- プロジェクトの規約ファイル（`CLAUDE.md`、レビュー規約など）を**先に読め**
- **重大度を Must / Should / Could で明示させ、`file:line`、故障条件、期待と実際の差、根拠（実行結果か仕様上の不変条件）を要求する。** 未実行の推測を「再現済み」と書かせない。
- 指摘を **実証済み / 静的に根拠あり / 未検証 / 反証済み** で区別させる。存在しない仕様を補完しない。差分以前からある問題は `既存問題` と区別し、今回の変更で悪化・露呈するかを説明させる。
- 指摘ごとに **同型の問題がほかにないか** 依存先・呼び出し元を含めて探し、個別修正で終わらせない。
- **「Must 0 件」「Should 0 件」なら明示的にそう書かせる**（沈黙と区別がつかないため）
- **内部でサブエージェントをフォークしたら、必ずその結果を待って畳んでから報告しろ**
- 最終報告は本文として返させる（ツール呼び出しだけで終わらせない）
- **修正を適用するな**

### テスト品質トラックにだけ書くこと

mutation は**テストが欠陥を検出できるかを確かめる実験**であり、Survived だけで実装バグともテストの欠陥とも断定しない。全分岐・全定数に全テストを掛ける方式を既定にしない。

1. 差分と変更の意図から、**見逃した場合に問題となる振る舞い**を列挙し、対応するmutationを選ぶ。優先: 認可条件、境界条件、公開APIの返り値、永続化・重複実行・状態遷移、キャッシュキー。無意味な文字列・等価変異・範囲外の定数は機械的に対象にしない。選定理由と省略範囲を台帳に残す。
2. **変異前のテストが通ること**を確認する。Mutationを1つ適用 → 影響するテストを優先して実行 → 必要に応じて統合テスト/全スイートで確認 → 直ちに復元、を繰り返す。テスト選択だけでは見逃す可能性があるので、重要なSurvivedや結果が疑わしい場合は対象を広げる。
3. **Killed / Survived / NoCoverage / Timeout / Invalid / Equivalent疑い** を区別して表で報告する。Survivedなら「本来変わるべき振る舞いか」「テスト入力・assertionが不足か」「等価か」を調査してから重大度を付ける。未実行はSurvivedと混ぜない。
4. Mutationを戻したら `git diff` と `git status` を確認する。**変更がある作業ツリーで対象ファイル全体をcheckoutして戻さない。**

可能なら、言語・既存環境に合うMutationツール（例: StrykerJS、PIT）を使う。変更範囲、テストカバレッジ、incremental実行を利用できるが、キャッシュやテスト選択には前提がある。ツールが無ければ手動で**少数の高価値なMutation**を選ぶ。全件テストが回せない場合は未検証範囲を明示する。

> 実績: test 側の Must はほぼ全部これ由来。「出力形式の定数を別の値に変えてもフロントの全件が緑」「置換の再走査を戻しても全件緑」は、読むだけでは出てこなかった。

**差分がキャッシュ・メモ化を持ち込んでいたら、専用の確認を行う。** `WeakMap` / `Map` / `??=` による結果の持ち回しが対象。

> (a) **キャッシュを無効化する**（常に計算し直す）。純粋で決定的な計算のメモ化なら、振る舞いが同じなのは正常であり、性能・単純化の比較へ進む。ただしI/O、失効、負荷制御、レート制限などのキャッシュでは観測可能な挙動が変わり得るので「等価」と決め付けない。
> (b) **キーを粗くする**（複合キーの一部を落とす・キーを定数にする）。結果に影響する異なるキーの具体例を作って検証する。Survivedの場合はテストの検出能力とキーの不変条件を調べる。
> (c) 必要に応じて **失効・更新・並列アクセス・同一キーの競合**を試す。キーだけ正しくてもstale readや重複ロードは起こり得る。

> 実績: (b) で Must が出た。参照を解決する関数のキャッシュキーを `(定義, 項目)` から `定義` だけに
> 落としても**全件が緑**。実際には1つ目以外の全項目が参照切れ表記になる実害のあるバグだった。
> 一方 (a) は生存し、レビュアーは「キャッシュの有効性は無検証（許容範囲）」と Could に落とした。
> **その Could がユーザーの「このキャッシュ要る？」で覆った。** 下の「キャッシュは目的と実ワークロードで正当化させる」へ。

### 明示的な性質・故障モデルに基づく検証

不変条件が特定できた場合、テスト品質トラックは**既存テストがどの性質を保証し、どの条件を試していないか**も確認する。実装から推測した条件は仕様と照合し、勝手に「正しい仕様」にしない。

- 入出力の性質（例: 正規化の冪等性、encode/decodeの往復）が明確ならproperty-based testingや境界値の生成を検討する。生成テスト自体も、実際に主張した性質を検査しているか確認する。
- 分散・DB・並行処理の変更では、再送、途中停止、競合、部分失敗、トランザクション境界を**変更に関係する範囲だけ**故障モデルとして列挙する。必要なら並列テスト・fault injection・状態遷移検証を選ぶ。単純な構文mutationで代用しない。
- 外部システムが必要で実行できない性質は、保証済みと書かず台帳へ。「仕様から論理的に確認」と「実行で確認」は分ける。

## 2. 親の責務

### 直す前に、自分で再現する

**サブエージェントの指摘を鵜呑みにしない。** Must / Should は親が自分の手で確認してから直す。

- 「この TS の書き方はコンパイルが通ってしまう」→ 最小再現を書いて `tsc` に通す
- 「この入力でクラッシュする」→ `node -e` で再現する
- 「この値は改竄できる」→ 該当コードを grep して経路を追う

> 実績: 「エディタ用スキーマが古く30ファイルの作者が誤エラーを踏む」という指摘は、該当機能を使う定義がゼロで**前提が誤り**だった。逆に「引数によるコンパイル時の縛りは効かない」は `tsc` で再現でき、設計をやり直す根拠になった。

**反証できたものだけ**台帳の「却下」に理由付きで記録する。再現できない場合は、(1) 前提が誤っている、(2) 実験条件が足りない、(3) 実行環境が使えない、を分ける。(2)(3) は **未検証**として残す。静的な根拠しかない場合も、その根拠と限界を明記する。

指摘が正しいと確認できたら、まず同型の欠陥がほかにないか探す。局所的な1箇所だけ直すと次のラウンドで別の箇所が報告され続ける。

### mutation 由来の指摘を直したら、同じ mutation をもう一度当てる

テストを足しただけでは足りない。**足したテストがその mutation で実際に落ちることを親が確認する。** 落ちないなら、直したつもりのものが直っていない。

> 実績: 「`value: ""` の選択肢を持つフィクスチャを足した」あと、そのフィクスチャを丸ごと消しても
> 全件緑のままだった。テストが「空文字を返すこと」しか主張しておらず、ガードが先に空文字を
> 返すのでフィクスチャの有無で結果が変わらなかった。**次のラウンドの Should で検出された。**

**mutation を `git checkout <file>` で戻すな。** そのファイルに自分の修正が入っていると一緒に消える。python 等でその場で書き戻すか、自分の修正が入っていないファイルにだけ `git checkout` を使う。バックアップに `cp` を使う場合、`cp -i` alias でプロンプトに詰まって復元されないことがある（`git status` で必ず確認する）。

> 実績: mutation を戻すつもりの `git checkout` で、同じファイルに入れた `ItemId` 削除を1回失った。

### キャッシュは目的と実ワークロードで正当化させる

純粋で決定的な計算のメモ化で (a) が生存したら、**親が測る。** この種類のキャッシュは結果を変えないことが期待されるため、性能・計算量・複雑性のトレードオフを定量化する。その根拠が無いまま入っているキャッシュは、

- **バグクラスを1つ持ち込む**（キーの陳腐化。上の実績のとおり、全件緑のまま壊れる）
- そのバグを防ぐためのテストと不変条件を要求する
- コードを増やす

という確定のコストを、測っていない利益と交換している。

ただしI/Oキャッシュ、重複要求の抑制、外部APIの保護、負荷制御を目的とするキャッシュでは、レイテンシーだけでなく**バックエンドへの負荷、freshness、整合性、障害時の挙動**も根拠になる。計測不能を理由に即削除せず、目的と保証を確かめる。

純粋な計算のメモ化については手順は3つ。**3つ目を飛ばすな。**

1. **A/B で測る。** 複数の規模で測る。差が規模に比例して開くなら、キャッシュは計算量の問題を
   隠している（3へ）。
   **数字は必ず規模とセットで書く。規模の無い数字は計測ではない。**
   そのうえで「**その規模は現実に起きるのか**」をコード・仕様・既存データで裏取りする。
   裏が取れないなら「規模 N なら要る / 規模 M なら要らない」までしか言えない。
   **そこを飛ばして「消すと遅くなる」と報告するな。**
2. **割に合わなければ消す。** 消したら、そのキャッシュを守っていたテストのコメントが
   嘘になっていないか確認する（キャッシュ前提の記述が残る）。
3. **割に合っていた場合こそ、そこで止まるな。** 「なぜキャッシュ無しの経路がそんなに重いのか」を問う。
   重い理由が改善可能な計算量なら、まずアルゴリズム変更を検討する。根本を直してから
   測り直すと、キャッシュの根拠は消えることがある。**初回（キャッシュが効かない）も速くなる場合がある。**
   ただし計算の再利用自体が本質的な最適化なら、キャッシュを残すのが正しい。

**測り方を間違えると逆の結論が出る。** ミス側の計測に「毎回オブジェクトを作り直すコスト」を混ぜない。
同じオブジェクトを使い回し、キャッシュを通る経路と通らない経路だけを比べる。

> 実績: 同じ PR に2つキャッシュがあった。片方は割に合わず削除。もう片方は
> **項目301件で 6.35ms** 掛かり、その規模では正当化された。そこで3を実行したら、解決関数が
> 毎回全項目を絞り込んでおり **O(項目数²)** だった。根本を O(1) に直すと同じ条件で 0.20ms になり、
> キャッシュの根拠も消えて両方消せた。初回（キャッシュが効かない）も速くなった。
>
> **ところがこの「正当化」は規模に全面的に依存していた。** 同じ計測で 101 件なら 0.47ms、
> 21 件なら 0.03ms。**ユーザーに訊いたら現実の規模は 301 件よりずっと小さく、
> O(項目数²) はそもそも問題ではなかった。** 仕様にも実装にも上限が無く典型規模の資料も無いまま、
> 301 件という自分で振った数字を根拠に「消していたら退行だった」と報告していた。
>
> 残ったのは「2つのキャッシュが消えて -29 行、キーの陳腐化というバグクラスが1つ消えた」という
> **単純化の利得だけ**で、性能は現実規模では前後とも誤差だった（再レンダーはむしろ
> 0.002ms → 0.080ms と遅くなっている）。**結論は変わらなかったが、根拠は全部入れ替わった。**
> 性能を理由にすると、規模の裏取りを怠った瞬間に根拠ごと崩れる。
> **キャッシュを消す理由は、まず単純化で立てろ。性能はその裏取りが済んでから足せ。**
>
> なお最初の計測は定義の構築コストを混ぜており、**逆の結論をユーザーに報告していた。**

### 修正の優先度

- **Must / Should は必ず対応を検討する。** 直さない・検証できない場合は台帳に理由・危険度・未実施の検証を書き、ユーザーに報告する。根拠不足の指摘は確認前に修正しない。
- **Could は ROI で判断。** コメント1行・テスト1行で閉じるものは拾う。挙動を変えるもの・既存のリファクタに波及するものは見送って記録。

### docs とコメントの修正こそ裏を取る

コードの修正はテストと型が受け止めるが、**docs とコメントは何も受け止めない。** 「〜には X を使え」「〜も対象」と書き足すときは、その X / その対象を**実際に動かして確かめる。**

> 実績: 3件の重い指摘のうち2件が、親が前のラウンドで入れた docs 修正の退行だった。
> - 「この検証に引っかかったら `.value` を使え」と書いたが、直前で名指しした項目の `value` は
>   内部ID。従うと画面にIDが出る定義が出荷される
> - 「この項目の行も参照先に使える」と書いたが、その項目の定義側 label は内部コード名で、
>   利用者が見る文字列は実行時に組み立てられる別物だった
>
> どちらも「対象を列挙する」「代替を案内する」という**親切のつもりの加筆**で入った。
> 列挙と案内は、断定した瞬間に検証対象になる。

### 書き込むのは親だけ

レビュアーは worktree 内でのみ書き換え、本体ツリーへの修正は親が行う。並行して修正エージェントを走らせない。

### 各ラウンドの終わりに

指摘ごとに、修正 → 影響するテストを通す → **コミットする** → 台帳の「対応済み」にそのコミットを書く。同じ変更で直る指摘（同一原因のもの）は1コミットにまとめてよいが、ラウンドの修正を1コミットにまとめない。まとめると、どの変更がどの指摘を直したのかを追えず、台帳からも修正を指せない。ラウンドの修正が揃ったら検証コマンド一式を通し、落ちたらその修正も1コミットにする。

直した指摘について **同じ再現手順で修正前後を比較**し、mutationなら再適用してテストがKilledになることを確かめる。変更前の不具合が確認できない指摘は「直った」と断定しない。テスト数だけではなく、何の性質が検証済みかを書き残す。

**コミットメッセージにラウンド番号を書かない。** 「レビューループ R2」「R3 対応」のような
ループ内部の進行状況は、履歴に残す価値のある情報ではない。読み手が知りたいのは
**何を直したか**だけで、それが何巡目の指摘だったかは無関係。

```
NG: fix: 再掲のレビューループ R2（lint の退行・古い名指し・弱いテスト）
OK: fix: lint の退行・古い名指し・弱いテスト
```

同じ理由で「レビュー指摘対応」「セルフレビュー対応」だけの件名も避ける。直した内容を書く。
リポジトリの規約でスコープ（機能名）を件名に入れている場合はそれに従う。

## 3. 収束判定

### レビュー範囲を段階的に変える

- **R1:** `base...HEAD` 全体を、周辺コード・意図・仕様に照らしてレビューする。
- **R2:** 全体の整合性を見直しつつ、前ラウンドの修正、未解決指摘、その影響先を重点的に見る。
- **R3以降:** 原則として**直前ラウンドのレビュー入力SHAから修正後SHAまでの差分 + その影響先 + 未解決指摘**をレビューする。ただし新しい故障クラスを見つけた場合、影響先が広い場合、前のレビューの前提が崩れた場合には対象を広げる。**差分限定=その差分の行しか読まないことではない。**

毎ラウンド、台帳を読んで指摘を重複排除する。Must/Shouldを1件修正するときは、同一原因の指摘をまとめて修正する。意図的に見送った項目を再提起するには新しい証拠が必要。

### 停止と未解決の扱い

```
Must/Should 0件かつ必須検証が完了      → 収束として4へ
Must/Should 0件だが環境等で検証不能     → 検証不完全として4へ。再レビューで解決しない欠落を記録
Must/Should が残り、4ラウンド未満       → 修正して再レビュー
4ラウンド到達                        → 残存リスクを分類し、打ち切る
```

**上限4ラウンド。** 3ラウンド目でも同じ種類の欠陥が続く、あるいは異なる層へ次々に波及する場合、局所的な修正を増やす前に**設計の前提・スコープ・欠陥クラス**を再点検する。件数が減らないことだけで「同じ問題を巡回している」と判断しない。

4ラウンド到達時は、**安易に「収束した」と言わない。**

- 未解決がShouldだけなら、理由と影響範囲を台帳に記録し、通常どおり4へ進む。単純化で未解決箇所を変更することは避ける。
- **Mustが残る、または高リスクな不変条件が未検証**なら、修正済み・安全だと報告しない。危険な範囲の単純化をスキップし、検証できる他の処理のみ進める。**完了後、マージ/リリースを推奨できない理由と必要な判断を明示する。** エージェントだけで承認したことにしない。
- 環境都合で確認できない事項は、Must/Shouldが0件でも「未検証」として報告する。レビュー指摘0件は安全性の証明ではない。

打ち切った場合、残っている指摘と収束しない理由（設計に無理がある／スコープが大きすぎる／同じ箇所を巡回している／検証環境が不足している）を最終報告に書く。

> 実績1: 5ラウンドで収束。ラウンドごとの Must+Should は 8 → 5 → 7 → 5 → 1 → 0。
> **3ラウンド目以降も Must が出た**ので、2ラウンドで切り上げていたら退行を見逃していた。
> 一方で最後の1件は既存の分岐だったので、上限は4が妥当。
>
> 実績2: Must+Should が 6 → 2 → 2 → 2 で止まらなかった回。数字が動かなくても
> **レビュアーが同じ場所を巡回していたのではなく、毎回別の層に降りていた**
> （実装 → フィクスチャ → docs の案内 → 第1層スキーマ）。
> 「Should が減らない」は打ち切りの理由になるが、**巡回しているかどうかは件数ではなく
> 指摘の中身で判断する。**

### 収束したら Fable と Codex に1回ずつ読ませる

収束または打ち切りの判定の後、4 に進む前に、Opus のラウンドとは別のモデルに**1回ずつだけ**読ませる。同じモデルのレビュアーどうしは、同じ前提に立って同じものを見落としやすい。2つは互いの結果を待たないので、**同じメッセージで同時に**起動する。

- **Fable:** Agent ツールに `model: "fable"` を渡し、1 のレビュアーと同じく `<base>...HEAD` の全体を読ませる
- **Codex:** Bash で、バックグラウンドで実行する。数分かかる

```bash
git status --short            # 未コミットの変更があれば先にコミットする
codex review --base <base> -c model=gpt-6-astra -c review_model=gpt-6-astra -c model_reasoning_effort=high   # <base> は 0 で固定した SHA
```

`review_model`も渡す。Codexはレビューのモデルを`review_model`から先に決めるので、設定ファイルに`review_model`があると、`model`だけでは別のモデルが読む。

- Fable に渡すのは差分と変更の意図だけにする。台帳やここまでの結論は渡さない。Codex にもプロンプトを足さない。同じ前提に引きずられると、別のモデルに読ませる意味がなくなる
- Fable と Codex の指摘も、ラウンドの指摘と同じに扱う。直す前に自分で再現し（2）、台帳で重複を除き、採らないものは理由を書く
- 直したら、修正差分と影響先に、Opus で差分限定のレビューを1ラウンドだけかける（範囲は3の R3 以降と同じ）。Fable と Codex はもう呼ばない
- `codex` が無いとき、ログインしていないときは Codex だけ飛ばし、最終報告に「Codex のレビューは未実施」と理由を書く

## 4. ponytail-review → simplify → 文書の推敲

収束または打ち切りの判定後に**1回だけ**かける。未解決Mustや高リスクの未検証箇所には挙動変更を伴う単純化を適用しない。順序が逆だと、直し続けている最中のコードを整理することになって無駄が出る。推敲も同じで、ラウンド中は docs の中身が動くので、整えた文章が次のラウンドで書き換わる。simplify がコメントや docs に触ることもあるので、推敲は simplify の後に置く。

### 4-1. ponytail-review で削除候補を列挙する

サブエージェントに `ponytail:ponytail-review` スキルを実行させる。対象コミット範囲は 0 で固定したものをそのまま渡す。

過剰実装（再発明された標準ライブラリ・投機的な抽象・実装1つのインターフェース・死んだ設定）だけを `file:L<行>: <tag> <削るもの>. <代わり>.` の1行形式で列挙させる。**適用はさせない**（このスキルは元々適用しない）。

correctness とテスト品質の2トラックは「壊れているもの」を探すため、**動くが要らないもの**を構造的に拾えない。ラウンド中の3トラック目にはしない — 直し続けている最中のコードに対する削除提案は、次のラウンドで消えるコードを指すだけで無駄になる。

### 4-2. simplify に渡して適用する

サブエージェントに `simplify` スキルを実行させ、**4-1 の出力をそのまま渡した上で**、**ハード制約を明記する**。ここまでのラウンドで確立した設計判断を、simplify が「単純化」として巻き戻すことがある。

ponytail-review の指摘のうち、ハード制約と衝突するもの・意図的に見送ったものは台帳の「見送り」に理由付きで記録し、simplify には「この指摘は適用するな」と明示する。

```
以下は全てレビューで確立した意図的な設計。元に戻すな:
- <制約1と、それがなぜ必要か>
- <制約2>
...
テストを消すな。適用後に検証コマンド一式を通し、落ちたら該当の単純化を戻せ。
既存テストの変更が必要なら、**テストが公開仕様を検証しているか、実装詳細に依存しているか**を先に調べろ。公開仕様の期待値を都合よく書き換えるな。実装詳細に結合したテストは、仕様不変を独立に確認できる場合に限り変更してよい。根拠が不十分なら単純化を戻せ。
行数が減っても読みにくくなったものは単純化ではない。戻せ。
コミットはするな。
```

適用後は**親が diff を自分で読んでから**、ponytail-review の指摘ごとにコミットを分ける（同じ変更で直るものはまとめてよい）。「コメント整理だけ」と報告されても、挙動変更が紛れていないか確認する。

### 4-3. 文書の推敲（ドキュメントと PR/MR 本文）

`prose-polish` スキルを実行する。渡すもの:

- **base:** 0 で固定した SHA。`<base>...HEAD` で追加・変更された `*.md` `*.mdx` `*.txt` `*.adoc` などのうち、変更箇所に日本語か英語の地の文があるものが対象になる。
- **PR/MR 本文:** PR/MR が無ければ対象外とし、最終報告にそう書く。
- **作業ディレクトリ:** 台帳のディレクトリの`prose/`。5 の最終確認で `.orig` と `.final` を読み比べる。
- **台帳のパス:** 採らなかった変更は「推敲で採らなかった変更」に書かせる。

ドキュメントの反映は、検証コマンド（docs の lint 等があれば）を通してコミットする。件名は直した内容を書く（例: `docs: <対象> の説明を整える`）。

## 5. 最終確認レビュー

4 の後に**1ラウンドだけ**レビューをかける。主目的は「4 の削除・単純化・推敲が大事なものを落としていないか」。

- 消えた根拠が他の場所から復元できるか
- 新しく張られた参照（「〜を参照」）が実在して、かつ正しいことを言っているか
- コメント編集を装った挙動変更が無いか
- 推敲で docs の主張・条件・確度・手順が変わっていないか、原文に無い説明・例が足されていないか(台帳のディレクトリの`prose/`にある`.orig`と`.final`を読み比べさせる)
- PR/MR 本文が最終の差分と合っているか。特に「確認したこと」に、実際には通していない検証が書かれていないか

ここで Must / Should が出たら**必ず再現・根拠確認して**対応し（PR/MR 本文なら、直した本文で 4-3 の更新と取得し直しの確認をもう一度行う）、出なければ終了。追加の修正に対して全ラウンドをやり直す必要はないが、**修正箇所と依存先に的を絞った検証**を行い、未検証事項を増やさない。4ラウンド上限を理由にこの最終確認を黙って省略しない。

## 失敗モード集

| 症状 | 原因 | 対処 |
|---|---|---|
| 範囲外のファイルの指摘が返る | ベース ref の取り違え | コミット範囲を明示、`master` との diff を禁止 |
| 報告の後に「addendum」が届く | レビュアーが内部でフォークした背景エージェントを待っていない | 「フォークしたら待って畳め」を指示に入れる |
| 本体ツリーが勝手に dirty になる | レビュアーの mutation が本体を触っている | `isolation: "worktree"` |
| 同じ指摘が毎回出る | 「対応済み/見送り」が伝わっていない | 台帳ファイルのパスを渡す |
| プロンプトが肥大化する | 経緯を毎回手で書き継いでいる | 同上 |
| 自分の修正が退行を生む | 修正後の再レビューをしていない | ラウンドごとに必ず再レビュー（**今回、自分で入れた退行を次ラウンドの Must で検出した**） |
| docs の加筆が退行になる | 列挙・案内を検証せずに書いた | 断定を書いたら動かして確かめる |
| 全レビュアーが最初の10分を同じ調査に使う | worktree の HEAD / `node_modules` / 通らない検証コマンド | プロンプトと台帳に先回りして書く |
| mutation を戻したら自分の修正も消えた | 同じファイルに `git checkout` を当てた | その場で書き戻す。`git status` で確認 |
| 「テストを足した」が効いていない | 足したテストを mutation で検証していない | 直したら同じ mutation をもう一度当てる |
| 要らないメモ化が残る | 無効化mutationが生存しただけで検討を止めた | 純粋な計算なら性能・複雑性を比較。I/Oキャッシュなら負荷・整合性の目的も確認 |
| キャッシュを消したら遅くなった | 「割に合う」で止まり、なぜ重いのかを問わなかった | 割に合った場合こそ計算量を疑う。根本を直すとキャッシュごと消えることが多い |
| 性能の結論が逆になる | ミス側の計測にオブジェクトの構築コストを混ぜた | 同じオブジェクトを使い回し、キャッシュの有無だけを比べる |
| 「消すと遅くなる」が独り歩きする | 数字を規模と切り離して報告した | 数字は規模とセットで書き、**その規模が現実に起きるか**を裏取りする |
| いつまでも終わらない | 停止条件が無い | Must / Shouldと必須検証の状態で判定し、上限4ラウンド。残存リスクを明示 |
| MutationのSurvivedをすべてバグと扱う | 等価変異・未カバレッジ・実行失敗を区別しない | 変異の意味、実行テスト、結果区分を記録してから重大度判断 |
| Mutationが遅すぎる | 全定数×全スイート実行 | 高リスクな性質を優先し、カバレッジベースのテスト選択とincremental実行を検討 |
| 回すたびに昔の別問題が出る | 全差分を毎回無差別に探索 | R3以降は修正差分+影響先+未解決を中心にし、同一原因をまとめて修正 |
| レビューが通ったのに保証を説明できない | 指摘件数だけで終了判断 | 仕様根拠・検証結果・未検証条件を台帳と報告に記載 |
| キャッシュの無効化で挙動が変わる | I/O・負荷制御キャッシュを純粋なメモ化と混同 | キャッシュの目的、失効条件、整合性、負荷の影響まで確認 |

## 報告

最後にユーザーへ以下を伝える。

- 変更のリスク区分、各ラウンドのレビュー対象範囲、Must / Should の件数（収束の様子が分かる形で）
- 重要な指摘ごとの **故障条件・根拠（実行/静的/未検証）・修正後の確認結果**
- mutationの **選定範囲・結果区分・省略範囲**、不変条件/故障モデルのうち検証したものと未検証のもの
- 特に効いた指摘（**自分で作り込んだ退行があれば隠さず書く**）
- 意図的に見送った項目と理由
- Fable と Codex の指摘の件数と、それぞれの扱い（直した／却下した／見送った）。Codex を飛ばしたなら理由
- 台帳の「申し送り」— 仕様・前提レベルの食い違いは独立した項として明示する
- **通せなかった検証コマンドがあれば、何が未検証のまま残っているかを書く**
- 上限4ラウンドで Should が残ったまま進んだ場合は、残件と収束しない理由
- 台帳のディレクトリの絶対パス。`ledger.md`と`findings.tsv`がそこにある
- prose-polish の報告（推敲したファイル、PR/MR 本文の更新と控えのパス、採らなかった変更、確かめたい点、検査の結果、humanizer のパス数）
- 取得できる場合は総レビュー実行時間・mutation実行数とKilled数。**件数とmutation scoreだけで品質を断定しない。**

### SKILL自体の改善は別の評価ループで行う

通常実行のたびに追加エージェントを走らせるのではなく、定期的に既知バグ・実際の不具合・リバートから**独立した評価セット**を更新する。可能なら既知のクリーンなPRも含める。通常レビュー/現行SKILL/変更後SKILLを同じコミットに適用し、バグの検出、誤検知、有害な修正、見逃し、時間、使用量を比較する。評価時の正解はレビュアーに渡さず、モデル・ツール・プロンプト変更の影響を測る。評価データの漏洩や未知の不具合が混ざる可能性も記録する。

# 台帳の型

`ledger.md`に、次の節を作って追記していく。検証コマンドとmutationの結果は、同じディレクトリの`evidence.tsv`に`evidence.sh`が記録するので、台帳には書き写さない。

```markdown
# 対象とリスク
- base SHA / 開始時のHEAD / 各ラウンドの入力のSHAと修正後のSHA
- 変更の意図 / 壊してはいけないもの(仕様か、仮説か)
- リスクの区分と理由 / 高なら、検証できる不変条件
- 検証コマンドと、その名前(`evidence.sh`の`run`に渡すもの)
- 終了: <報告を書いたときのHEADのSHA>(報告を書いたら足す)

# 環境の注意・未検証
- <通らない検証コマンドと、その代わり、影響を受ける機能>

# 対応済み
- [R1-correctness/Must/start] <内容> → <どう直したか>(<直したコミット>)

# 意図的に見送り(出し直しは、新しい論拠があるときだけ)
- [R1-test/Could/start] <内容> → <理由>

# 申し送り(この変更の範囲の外。別に判断が要る)
- [R2-correctness/Could/pre-existing] <内容> → <なぜここに入れないか>

# 却下した指摘(前提が誤っていたもの)
- [fable/Should/start] <内容> → <何が誤りだったか>

# 推敲で採らなかった変更
- <ファイルかPR本文> <推敲案> → <採らなかった理由>

# 指摘と検証証拠
- R1/Should: <種類、file:line、影響する条件> → <実証済み / 静的に根拠あり / 未検証 / 反証済み>、<再現のコマンドか仕様の根拠>、<結果>

# mutation・性質の検証
- <見逃すと問題になる振る舞いの一覧、選んだ理由、省いた範囲と理由>
- <Survivedと、Equivalentの疑いの論拠、結論>
```

- 「見送り」と「申し送り」は分ける。「見送り」はレビュアーに出し直させない一覧で、「申し送り」は利用者への報告の対象になる。混ぜると、仕様の水準の発見が見送りに埋もれる。
- 「未検証」は「誤りなので却下」とは違う。環境や仕様が足りずに確かめられなかった指摘を、再現できなかったという理由だけで消さない。

## 行の印

「対応済み」「見送り」「申し送り」「却下」の行の先頭には、`[工程/重大度/由来]`を付ける。どの工程が何を見つけたかを、後で大まかに数えるための印で、厳密な件数は求めない。

- 工程: 指摘を出した工程。`R1-correctness`、`R1-test`(R2以降も同じ形)、`fable`、`codex`、`followup-correctness`、`followup-test`(FableとCodexの指摘を直した後の確認)、`final-correctness`(最終ゲートで`FAILED`を直した後の確認)、`ponytail`、`simplify`、`prose`(prose-polishの報告から直した)、`parent`(親が自分で見つけた)、`user`(利用者が出した)。複数の工程が出したら`+`でつなぐ
- 重大度: 親が扱いを決めたときの`Must`、`Should`、`Could`。重大度を付けない提案は`-`
- 由来: `start`(レビュー対象の差分が持ち込んだ)、`fix`(ループの中の修正、単純化、推敲が持ち込んだ)、`pre-existing`(差分より前からある)

# mutationと性質の検証

mutationは、テストが欠陥を検出できるかを確かめる実験。`Survived`だけでは、実装の欠陥ともテストの欠陥とも決めない。全部の分岐と定数に全部のテストをかける方式は取らない。

## 選ぶ

1. 差分と変更の意図から、**見逃すと問題になる振る舞い**を7つまで挙げる。優先するのは、認可の条件、境界の条件、公開APIの返り値、永続化、重複した実行、状態の遷移、キャッシュのキー。
2. 振る舞いごとに、変異を1つか2つ選ぶ。合わせて通常は15個まで、高は30個まで。意味の無い文字列、等価な変異、範囲の外の定数は選ばない。
3. 挙げた振る舞い、選んだ理由、省いた範囲を、報告に書く。親が台帳に写す。

## 回す

変異は1つずつ、unified diffのパッチのファイルにする(台帳のディレクトリの`mutations/<ラウンド>-<名前>.patch`。作業ツリーの中には置かない)。同じ名前のファイルを上書きしない。直した後に、親が同じパッチを当て直すため。直した後に同じパッチが当たらない(`Invalid`)ときは、同じ変異を今のコードで作り直し、元の名前の番号の後ろに`-v2`を入れた名前(`r2-m03-trap.patch`なら`r2-m03-v2-trap.patch`)で回して、`Killed`になることを確かめる。

`git apply`が当てるのは、リポジトリの最上位からの相対パスに`a/`と`b/`を付けたパッチ(`git diff`の形)だけ。作業ツリーを書き換えずに作るには、対象のファイルの写しを書き換えて、次のように作る。差分があると、`diff`は終了コード1で終わる。

```bash
diff -u --label a/<パス> --label b/<パス> <元のファイル> <書き換えた写し> > <パッチ>
```

回すのは`evidence.sh`に任せ、手で当てたり戻したりしない。

```bash
bash <スキルのディレクトリ>/scripts/evidence.sh <台帳のディレクトリ>/evidence.tsv mutate <パッチ> -- <テストのコマンド>
```

- 作業ツリーに未コミットの変更か未追跡のファイルがあると、何もせずに終わる。先にコミットする。
- 出力を`| head`などのパイプで切らない。読み手が先に閉じると、その後に書き出したテストのコマンドがSIGPIPEの141で終わり、`Killed`として記録される。
- 変異を当てる前に、同じコマンドが通ることを確かめる(基準の実行)。通らなければ`Invalid`になる。同じ指紋と同じキー(作業ディレクトリ、コマンド、`MUTATE_BUILD`、`MUTATE_TIMEOUT`)の基準の実行が、最後に成功していれば省かれる。`run`で同じコマンドを回した記録は使わない。
- 結果は`Killed`(テストが落ちた)、`Survived`(テストが通った)、`Timeout`、`Invalid`(パッチが当たらない、基準の実行が通らない、ビルドできない、変異の実行が126か127で終わる)。126と127は、ふつうはコマンドを実行できなかったことを表すので、`Killed`にしない。ただし、テストが変異で消えた関数を呼んで127で終わったときも`Invalid`になり、その場合はテストが変異を検出している。126か127の`Invalid`は、`mutate`が表示したテストの出力から、何を実行できなかったのかを手で確かめる。
- ビルドが要る言語では、環境変数`MUTATE_BUILD`にビルドのコマンドを渡す。ビルドの失敗は`Invalid`になり、`Killed`と混ざらない。
- 時間の上限は、環境変数`MUTATE_TIMEOUT`に秒で渡す。`timeout`のコマンドが無ければ、何もせずに終わる。
- パッチは`git apply -R`で戻され、戻した後のツリーが当てる前と同じかを確かめる。違えば、終了コード5で止まるので、そのまま続けない。
- パッチを当てる直前から、戻してビルドし直したツリーを確かめるまでの間に、シグナル(HUP、INT、TERM)を受けたときは、実行中のコマンドが終わるのを待ってから、パッチがまだ当たっていれば(順向きに当たらなければ)戻す。`MUTATE_BUILD`があればビルドし直し、同じように確かめて、終了コード130で終わる。結果は記録しない。
- Claude CodeのTaskStopなどで止めても、Windowsでは`evidence.sh`が止まらず、変異を当てたまま裏で動き続けることがある。止めたときは、`git status`と、`evidence.sh`のプロセスが残っていないか(`ps -ef | grep evidence.sh`)を確かめてから続ける。

影響するテストだけを回すと、見逃すことがある。重要な`Survived`や、結果が疑わしいものは、統合テストか全件で回し直す。使い回しているサーバーやビルドのキャッシュが、変異を拾っていないことがある。変異を当てても結果が変わらないときは、まずそれを疑う。

## 読む

- `Survived`は、本来変わるべき振る舞いか、テストの入力か期待値が足りないのか、等価な変異かを調べてから、重大度を付ける。
- 等価かどうかは、論拠を書いた「Equivalentの疑い」として残す。`Survived`を黙って落とさない。
- カバレッジのデータが無いときは、`NoCoverage`と決めずに`Survived`として扱う。
- 言語に合うツール(StrykerJS、PITなど)があれば使ってよい。差分に絞る機能とキャッシュには前提があるので、確かめてから使う。

## 性質と故障モデルの検証

不変条件が特定できた場合、テスト品質トラックは**既存テストがどの性質を保証し、どの条件を試していないか**も確認する。実装から推測した条件は仕様と照合し、勝手に「正しい仕様」にしない。

- 入出力の性質（例: 正規化の冪等性、encode/decodeの往復）が明確ならproperty-based testingや境界値の生成を検討する。生成テスト自体も、実際に主張した性質を検査しているか確認する。
- 分散・DB・並行処理の変更では、再送、途中停止、競合、部分失敗、トランザクション境界を**変更に関係する範囲だけ**故障モデルとして列挙する。必要なら並列テスト・fault injection・状態遷移検証を選ぶ。単純な構文mutationで代用しない。
- 外部システムが必要で実行できない性質は、保証済みと書かず台帳へ。「仕様から論理的に確認」と「実行で確認」は分ける。

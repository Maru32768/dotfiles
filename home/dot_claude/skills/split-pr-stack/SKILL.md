# 大きい PR を、積んだ子 PR に分ける

## 形

- 統合用のベースブランチと、ベース PR（Draft）を作る。子 PR はここに集め、QA はベース PR で 1 回だけ行う
- 子 PR は 1 本の線に積む。1 本目だけがベースに向き、残りは 1 つ下の子 PR に向く
  - 依存先が複数ある層があると、全部をベースに向けたとき、依存先の変更が差分に混ざる。線に積めば、各 PR の差分はその層の変更だけになる
  - 依存の無い準備の層を下に置き、何からも依存されない層を一番上に置く
- マージは表の番号順に、merge commit で行う
  - マージ後にブランチが自動で消える設定なら、下の PR がマージされたとき、GitHub が上の PR の base を付け替える
  - squash すると、上の PR の差分に下の PR の変更が混ざる

## 手順

### 1. 層とファイルの持ち主を決める

層の順番、層の依存、ファイルの持ち主の表を用意する。ship-task の 3 で作った表があれば、それを使う。

共有ファイル（複数の層が変えるファイル）は、各層での中身を「最終の中身から、上の層の部分を取り除いたもの」として定義する。取り除く単位は、import の行、関数、テスト関数、表の行、列挙子など。

### 2. 層ごとのブランチを作る

- 作業は scratchpad の git worktree で行う。利用者の作業ツリーと、同じ名前の既存ブランチには触らない。名前が空いているかは `git branch --list` と `git ls-remote --heads origin` で確かめる
- `scripts/build_layers.py` を作業ディレクトリに写し、`FINAL`、`BASE`、`ORDER`、`OWNERS`、`TRANSFORMS` を埋める
  - 層 L でのファイルの中身は次のとおり。最初の持ち主より下の層では BASE のまま、最後の持ち主以上の層では FINAL のまま、その間の層では TRANSFORMS で FINAL から上の層の部分を取り除く
  - BASEとFINALからは`git restore`で取り出すので、モード、シンボリックリンク、バイナリもそのまま移る。TRANSFORMSで変換する共有ファイルは、テキストに限る
  - 取り除く処理は、どれも「ちょうど 1 か所に当たる」ことを assert する。当たらなければ止まるので、黙って壊れた層はできない
- まず全層を順に書き出すドライランをする。最後の層で `git add -A && git diff --cached --stat --exit-code <FINAL>` が0で終わることを確かめ、`git reset --hard` で戻す
- ベースブランチに空コミットを 1 つ作る。GitHub は、差分の無い PR を作れない
- 層ごとに `git switch -c <ブランチ>`、スクリプト、commit を繰り返す。元のコミットのメッセージが使える層は、それを流用する

共有ファイルの変換は、たとえば次のように書く。

```python
def t_tools_test(t):
    if below("B5"):
        t = cut(t, '                "register_widget" to Triple(false, true, true),\n')
        t = cut_test(t, "登録すると一覧に出る")
    if below("B3"):
        t = cut_lines(t, "    companion object {", "    }")
    return t
```

### 3. 各層を検証する

- `scripts/verify.sh` を写し、末尾に層ごとの検査の行を書いて、バックグラウンドで回す。層ごとに compile、lint、その層のテストを回し、影響範囲の広い層とスタックの先端は全件を回す
- 結果の `rc` が 0 でない層は、ログを読んで原因を確かめる。テスト自体は通っていて、検査コマンドの書き方で落ちていることがある
- 生成物をコミットしているリポジトリでは、ビルドの後に `git status` が空であることも確かめる。空なら、生成物と元の定義が食い違っていない
- 最後に、先端のツリーが元のブランチと一致することをもう一度確かめる

### 4. 本文を作る

型は references/templates.md にある。

- 子 PR: 概要、なぜ要るか、なぜこの形か（選ぶ余地があれば）、変更、レビューの観点（あれば）、動作確認、この PR の位置（何本目か、ベース PR、直下の PR、先に読む PR、次にレビューする PR）、`Closes #<子 issue>`
- 子 PR の WHY は、その PR だけを読んで分かるように書く。分割すると、元の PR の背景や設計判断は一部の PR にしか移らない。前提が別の PR にある層（準備の refactor、ビルド設定、テストの helper など）ほど、何のための変更かが読み手に見えなくなる
  - 「なぜ要るか」には、この変更が無いと何が起きるか、誰が何のために必要とするかを書く
  - 「なぜこの形か」には、読み手が思いつく別の案と、採らなかった理由を書く
  - 書いたら、この会話の文脈を持たないサブエージェントに各子 PR の本文と差分を渡し、本文で答えていない WHY の問いを挙げさせる。答えはコード、コミット、issue、元の PR から裏を取って本文に足す。裏の取れない理由は書かない
- ベース PR: 概要、子 PR の表（番号、PR、issue、内容、先に読む PR）とレビュー・マージの進め方、運用、マージ前の作業、範囲外、テストケース、QA の定型文、`Closes #<元 issue>`
- 「先に読む PR」には、コードの前提になる PR だけを挙げる。テストでしか使わない依存は入れない
- 本文はすべて、サブエージェントに頼んで prose-polish に通す。推敲で出た事実関係の指摘は、自分で裏を取ってから直す。直した文は、もう一度 prose-polish に通す

### 5. 確認を取ってから公開する

push、PR の作成、元の PR を閉じることは、確認を取ってから行う。確認では、層の表、検証の結果、作るものの一覧、元の PR の扱いを見せる。

子 PR を Ready で作ると、AI レビューと CI が本数分走る。Draft にするかどうかは、利用者に選んでもらう。

`scripts/publish.sh` は写さずに使う。設定ファイル（項目はスクリプトの冒頭にある）、層の一覧（層、ブランチ、先に読む層）、本文のファイルを用意して、`bash <スキルのディレクトリ>/scripts/publish.sh <設定ファイル>` を実行する。中でやることは次のとおり。

1. 全ブランチを `--atomic` で push する
2. ベース PR を Draft で作る。ベース PR も子 PR も、Assignees は利用者（設定の `ASSIGNEE`、既定は `@me`）にする
3. 子 PR を下から作る。下から作るので、直下の PR と先に読む PR の番号が本文に書ける
4. 全部作り終えたら、各子 PR の本文を取り直して「次にレビューする PR」を埋め、ベース PR の表に子 PR の番号を書き込む
5. 元の PR をコメント付きで閉じる。ブランチは消さない
6. 全 PR の base、head、Draft かどうか、ファイル数、Assignees、未置換のプレースホルダを GitHub から読み直して表示する

表示された結果が層の表と合っているかを確かめる。

### 6. 公開後に本文を直すとき

bot（Devin など）が本文の末尾に追記する。ローカルのファイルで上書きせず、本文を取り直してから、該当箇所だけを置き換える。

## 落とし穴

- `Closes #N` は、デフォルトブランチに向けた PR でしか効かない。子 issue は手で閉じる
- ルールセットの必須チェックは、デフォルトブランチにしかかからない。子 PR は、CI が緑なのを自分で確かめてからマージする
- ベース PR が別の feature ブランチに向いている間に main を取り込むと、main の無関係な変更がベース PR の差分に入る。main を取り込むのは、ベース PR が main に向いてから
- zsh では、`$H:s…` の `:s` が修飾子として解釈される。変数の直後に `:` が続くときは `${H}` と書く
- `cp` が `-i` のエイリアスになっていることがある。上書きは `/bin/cp -f` で行う
- Gradle のマルチプロジェクトで `test --tests X` と書くと、サブプロジェクトのテストタスクにも効き、「No tests found」で落ちる。`:test --tests X` と書く

## リポジトリ固有の事実

ブランチの自動削除、必須チェック、ボード、ブランチ名、検証コマンドなどは、リポジトリの設定と `CLAUDE.md` から確かめる。

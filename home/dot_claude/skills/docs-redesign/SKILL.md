# 文書の再設計

文書を、書き手が持っている情報の順ではなく、読者が知りたい順に組み立て直す。直すのは、何を載せるか、どこに置くか、どの順に並べるか、どう説明するか。文の表面は、最後に`prose-polish`へ渡す。

優先順位は、事実が正しいこと、必要な記述が残っていること、読者が答えにたどり着けること、短さの順。構成に問題が無ければ、構成は変えない。

対象は、人が読む文書。`CLAUDE.md`、`AGENTS.md`、`SKILL.md`などのエージェントへの指示は対象にしない。

## 深さ

| 深さ | 使うとき | 進め方 | サブエージェント |
|---|---|---|---|
| 点検 | コードの変更に合わせた追記、数段落の更新 | 0と「点検」の節だけ | 起こさない |
| 再構成 | 1つの文書(README、1ページ)を組み立て直す。記述の移す先のページは足してよい | 0〜7 | 読者テストの2つ |
| 全体 | 複数のページ、ナビゲーション、READMEとガイドとサイトの分担 | 0〜7。4で必ず承認を取る | 読者テストの2つ。10ページを超えたら、台帳づくりをページの組ごとに分けてよい |

依頼の範囲で決める。迷ったら浅いほうにし、深いほうが要ると分かったら、その根拠を報告に書く。

## 0. 対象と規約

- 対象のファイルと種類を決め、種類の資料を読む。READMEは`references/readme.md`、ガイドと技術文書は`references/guide.md`、Webサイトは`references/website.md`。読むのは、対象の種類のものだけにする。
- プロジェクトの文書の規約(`CLAUDE.md`、`CONTRIBUTING.md`、スタイルガイド、表記の規則、対訳の決まり)を読む。この文書より優先する。
- 対象の派生を探す。対訳(`README.ja.md`など)、READMEを取り込むレジストリやサイトのトップ、文書の文言を固定しているテストやCI。構成を変えたら、派生も同じ構成に直す。対象の節を名指ししている記述(エージェントへの指示の中も含む)も探し、指している箇所だけを直す。
- 作業ディレクトリ`<work>`を作る。場所は、システムプロンプトにscratchpadのディレクトリが書かれていれば`<scratchpad>/docs-redesign/<名前>/`、無ければ`/tmp/docs-redesign/<名前>/`にする。WindowsのGit Bashでは、`cygpath -m`で直したパスを使う。変える前に、対象を`<work>/before/`へ、リポジトリからの相対パスのまま写す。後から変えると決めたファイルも、変える前に写す。

## 1. 読者と問いを決める

- 読者を1〜3種類決める。読者ごとに、この文書に来る直前の状況と、ここで決めたいこと、やりたいことを1文で書く。
- 読者がこの文書に尋ねる問いを、優先順に5〜8個書く。種類の資料に既定の問いがある。そのまま使わず、リポジトリの証拠(成果物の種類、issueや質問、既存の文書、利用者の説明)で選び直す。証拠が無く推測した読者と問いには、推測と書く。
- 問いごとに、正しい答えと根拠(コードの場所、実行の結果)を書く。根拠を示せない問いは、「利用者に確かめる点」に回す。
- 読者と問いで構成が大きく変わり、リポジトリからは決まらないときだけ、利用者に1回でまとめて尋ねる。それ以外は尋ねずに進め、置いた前提を報告に書く。
- `<work>/questions.md`に書く。問いは、構成の基準と、読者テストの問題を兼ねる。ここで決めたら、構成を変えた後に書き換えない。

## 2. 台帳を作る

`<work>/inventory.md`に、今の文書を2つの表にする。

- **節の表。** 節ごとに、見出し、行数、答えている問い(無ければ「無し」)、種類の資料にある役割。
- **記述の表。** 確かめられる記述を拾う。コマンド、フラグ、既定値、環境変数、設定のキー、パス、バージョンと対応環境、数値、動詞に隠れた振る舞い(「自動で再接続する」)。1件ずつ、定義している場所(引数のパーサー、設定のスキーマ、マニフェスト、テスト)を読むか、安全なら実行して、確認済み(根拠)、食い違い、未確認を付ける。記憶で付けない。
- **文書に無い記述。** 最初の成功までの道(入れ方、最初の1回の実行)は、コードの側からも読む。入口のスクリプトやコマンドの定義をたどり、文書に無い前提、手順の順、既定値、副作用を、記述の表に「文書に無い」として足す。

全部を確かめられないときは、上位の問いの答えになる記述、最初の成功までの手順、これから書き換える記述を先に確かめる。残りは、確かめていない範囲と件数を報告に書く。

## 3. 診断する

再構成と全体では、先に今の版の読者テスト(6の4)を起こし、返事を待つ間に診断する。大きいものから見る。

1. **仕事。** この文書(ページ)の仕事は1つか。ほかの文書の仕事を抱えていないか。
2. **欠け。** 答えが無い問い、答えはあるが見つからない問い、台帳で「文書に無い」とした記述。
3. **余り。** どの問いにも答えていない節。
4. **順序。** 節の順が、問いの優先順に合うか。前提や条件が、それを使う手順より後にないか。
5. **見出し。** 見出しだけを読んで、各問いの答えがどこにあるか当てられるか。
6. **重複と食い違い。** 同じ事実が2か所にあり、ずれていないか。README、ガイド、サイトの間でも見る。
7. **説明。** 例が無い、期待する結果が無い、定義より先に用語が出る。

指摘は「どの読者が、何を得られないか」で書く。枠組みに合わないこと自体は、指摘にしない。読者テストの結果は、欠けの証拠として使う。

診断の結論を、次の3つから選ぶ。

- 変えない。問題が見つからなかった。
- 構成は変えず、誤りと欠けだけを直す。
- 組み立て直す。

コードが正しいと言える食い違いは、どの結論でも直す。小さいことを、直さない理由にしない。変えないなら、ここで報告して終える。誤りと欠けだけを直すなら、4は変更表だけを書き、5と6へ進む。

## 4. 構成案を作る

- `<work>/plan.md`に、新しい見出しの木を書き、台帳の節と記述の1件ずつに行き先を付ける。残す、移す(先)、まとめる、削る(理由)。
- 削ってよいのは、重複、直せない誤り、どの読者も行動を変えない記述で移す先も無いもの。固有の技術的な記述は、削らずに移し、元の場所に1行の行き先を残す。
- 変更表を書く。変更、理由(どの読者のどの問いか)、読者への影響、リスク(変わるURL、壊れるリンク、派生への影響)。問いで理由を説明できない変更は、案から外す。
- 承認。全体では必ず取る。再構成では、ファイルの新設、改名、削除、URLやアンカーが変わる変更、固有の記述の削除があるときに取る。それ以外は、案を示してそのまま進める。
- 全体では、単独で出せる小さな単位(1つの分割、統合、移動、新しいページ)に分け、順に適用する。空の節や空のページを先に作らない。文書を使えない状態にする全面の書き直しをしない。

## 5. 書き直す

- 構成を大きく変える節は、継ぎ足さず、新しい見出しの木に沿って書き直す。
- 書いてよいのは、台帳で確認済みの事実と、今回コードや仕様で確かめた事実だけ。欠けを、もっともらしい文で埋めない。確かめられないことは、本文に入れず、「利用者に確かめる点」に回す。
- 足す行と書き直す行は、表記の規約に従う。プロジェクトに無ければ、利用者の指示にある規約を使う。どちらも無ければ、そのファイルの今の表記に合わせる。変えない行の表記は直さない。コードブロックの中は、事実の誤りを直すときだけ変える。
- 食い違いは、コードが正しいと言えるなら文書を直す。同じ誤りがほかの文書にもあれば、その箇所だけを直す。どちらが正しいか決められないなら、直さずに報告する。実装は変えない。
- 見出し、ファイル、URLを変えたら、そこを指すリンクとアンカーをリポジトリ全体から探して直す。節を移すか削ったら、その文書を指すアンカーの無いリンクと、文書の名前で呼んでいる地の文(「READMEの入れ方を見る」)も探し、指している内容がそこに残っているかを確かめる。
- コミットするなら、移動と並べ替え、事実の修正、文の書き換えを分ける。移動だけのコミットは、差分を読む人が中身の変化を探さずに済む。

## 6. 確かめる

1. **落ちた記述。** 次を回す。前の版にあって、後の版のどこにも無いコードの行、インラインコード、リンク先、URLが挙がる。`code`、`span`、`link`、`url`は1件ずつ、戻すか、移した先の場所か、削った理由を変更表に書く。`line`は、コードの行は無いが、その行の語はすべて後の版に残っているもの。前の版の節ごとにまとめて、移した先の例が同じ使い方を見せているかを確かめる。相対パスを書き直したリンクも挙がる。後の版のどこかに同じ文字列があれば挙がらないので、別の文脈に残っているだけの記述は見逃す。地の文の事実はこの検査に入らないので、台帳の記述の表で行き先を確かめる。

   ```bash
   bash <このスキルのディレクトリ>/scripts/lost.sh <work>/before/<ファイル>... -- <変えた後の関係するファイル>...
   ```

2. **事実。** 新しく書いた記述と書き換えた記述を、2と同じやり方で確かめ直す。既定値や、いつもそうなると読める文は、定義元の分岐(環境の検出、条件つきの既定)まで読み、条件を文に入れる。手順は、安全に実行できるものを、書いた通りに実行する。
3. **リンク。** プロジェクトのリンク検査(`mkdocs build --strict`、lycheeなど)があれば回す。無ければ、変えた見出しと移したファイルを指すリンクを、grepで確かめる。
4. **読者テスト。** `references/reader-test.md`を読み、今の版と後の版に、同じ問いで1回ずつかける。
5. プロジェクトの既存の検査(lint、ビルド、文言を固定しているテスト)を通す。環境の都合で落ちる検査は、変更と関係しないことを確かめて、報告に書く。

## 7. 推敲に渡す

構成が決まってから、変えた範囲を`prose-polish`に渡す。作業ディレクトリには`<work>/prose/`を渡す。ship-taskやreview-loopの中で使ったときは渡さない(review-loopの片づけが推敲する)。

## 点検

日々の更新で、変えた箇所だけを見る。

1. **追随。** `git diff <base>...HEAD`から、コードが変えた公開の面(コマンド、フラグ、設定、既定値、API、エラーメッセージ)を拾い、その名前で文書をgrepする。古いままの記述を直す。
2. **置き場所。** 足した記述は、その文書の仕事か。READMEに詳細を足していないか。同じ事実が既にほかにあれば、そこを直し、足した側はリンクにする。
3. **事実とリンク。** 変えた記述を2のやり方で確かめ、6の3を回す。
4. 構成の問題に気づいても、その場で組み立て直さない。報告して、再構成を勧める。

## 報告

- 深さ、読者と問い(推測したものは、そう書く)
- 変更表と、変えたファイルの一覧。変えなかったなら、その根拠
- 落ちた記述の検査の結果、移した記述の行き先、削った記述と理由
- 見つけた食い違いと扱い。確かめていない範囲と件数、回せなかった検査
- 読者テストの問いごとの前後。版ごとに「LLMの読者が、N問のうちM問に答えた」と書く。LLMの読者による結果で、人では確かめていないと書く。「読みやすくなった」とは書かない
- 利用者に確かめる点
- `<work>`の絶対パス

設計の根拠、借りた考え方、検証の結果は`references/background.md`にある。実行のたびに読む必要は無い。

# ユーザー向けWebサイト

サイトの仕事は、訪れた人が、何の製品か、自分に関係があるか、信じてよいか、次に何をするかを、この順に決められること。ページごとに、読者に取ってほしい主な行動を1つ決める。

見た目、レイアウト、アクセシビリティは扱わない(`web-design-guidelines`、`frontend-design`)。検索での順位も扱わない。

## トップページの既定の問い

| 問い | 答えになるもの |
|---|---|
| 何をする製品か | 何を入れると、何が出てくるか。具体的な1〜2文 |
| 誰の、どんな問題のためか | 読者が自分の場面だと分かる例 |
| 実物はどう見えるか | コード、画面、動く例。形容詞より先に実物を見せる |
| 信じてよい根拠は何か | 仕組み、制限、数値とその出どころ、ソース、ライセンス、価格 |
| 次に何をすればよいか | 試す、入れる、文書を読む。行き先を名指しした導線 |

機能、価格、導入の手順などのページは、そのページに来る人の問いを同じやり方で決める。

## 構成

- 最初の画面で、「何をする製品か」と「次に何をすればよいか」に答える。見出しは、標語ではなく、製品がすることを書く。
- 機能は、機能の名前の列ではなく、解ける問題で書く。
- 導線の文言は、行き先を言う(「5分で最初のコマンドを作る」「APIリファレンスを読む」)。「詳しくはこちら」「はじめる」は、行き先を予告しない。
- 技術者向けの製品では、文書、ソース、入れ方への導線を、最初の画面かその直後に置く。ライブラリや基盤の製品では、最初の画面にコードを置く。
- 価格、制限、対応環境を隠さない。登録しないと読めない情報は、信頼を下げる。置き場所を変えるかは製品の判断なので、変更表に提案として書く。
- 主な導線の行き先を替えること、コメントアウトしてある要素を戻すことも、製品の判断になる。変えずに、変更表に提案として書く。
- サイト、README、ガイドで、製品の説明の1文目と、機能や数値の主張を揃える。食い違いは、3の「重複と食い違い」に挙げる。

## 宣伝の文を事実に替える

次のどちらかに当たる文は、確かめられる事実に替える。替えられなければ消す。

- 競合の製品のサイトに、そのまま書ける(「強力で柔軟」「開発者のための次世代の」)
- 読者が確かめる方法が無い(最上級、出どころの無い数値や利用者の数)

替える先は、数値と測った条件、対応する範囲、仕組み、実物の例。事実が手元に無ければ作らない。何があれば書けるかを、「利用者に確かめる点」に書く。緊急性をあおる文、根拠の無い導入実績、測っていない効果を足さない。

機能の主張は、台帳の記述の表に入れ、コードか製品で確かめる。まだ出していない機能は、出した機能と分けて書く。

## 構成の読み方と書き方

- ソースから、内容の骨組みを書き出す。ページ(ルート)、節(コンポーネント)の並び、節ごとの見出し、本文、導線。これを、台帳の節の表にする。
- 動かせるなら、描画して確かめる。デスクトップとモバイルの幅で、最初の画面に何が出るかを見る。読者テストには、描画したページの本文を渡す。描画できず、コンポーネントのソース(MDC、JSXなど)から本文を書き出すときは、画面に出る文言を、出る順に並べる。コメントアウトしてある要素、設定のキー、クラス名は入れない。
- 構成の変更は、節の並べ替え、統合、ページの間の移動で行う。文言を変えるときは、コードを壊さない(JSXの中の文字列、翻訳のキー)。翻訳のファイルがあれば、全部の言語を揃える。
- `lost.sh`は、Markdownのコードブロックとインラインコードを見る。HTMLやJSXでは、`href="..."`と書いたリンク先と、`http`で始まるURLしか拾えない。文言の行き先は、台帳で確かめる。
- ソースが無く、公開されたページしか見られないときは、変えられない。診断と構成案だけを報告する。

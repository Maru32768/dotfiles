# README

READMEの仕事は、初めて来た人が、これは何か、自分に関係があるか、どう試すかを決められるようにし、その先へ送ること。使い方の全部を載せる場所ではない。

## 既定の問い

読者と成果物に合わせて選び直す。

| 問い | 答えになるもの |
|---|---|
| これは何をするものか | 何をするかを、使っている技術の名前より先に、1〜2文で書く。何の代わりになるか |
| 自分に関係があるか | 誰の、どんな場面のためか。向かない場面と、そのときに使うもの |
| 自分の環境で使えるか | 対応するOS、言語、バージョン、依存、ライセンス |
| いまの状態は | 実験的か安定か、保守されているか。確かめられる事実で書く |
| 最短で動かすには | 前提、入れ方、最初の1回の実行、期待する結果 |
| 詳しいことはどこにあるか | やりたいことごとの行き先 |
| 困ったとき、手を入れたいときは | 質問の場所、貢献の手引き |

「何か」と「どう使うか」はたいてい書いてある。欠けやすいのは、「なぜこれを選ぶか、いつ選ばないか」と「いまの状態」。

読者が外の利用者でないリポジトリ(個人の設定、社内のツール、アプリの本体)では、読者は将来の自分、同僚、新しく入った人になる。「なぜ選ぶか」は要らないことが多く、「どこから手を付けるか」「どこに何があるか」「よく使うコマンド」が上位に来る。

## 順序

- 読者が「自分向けではない」と早く決められる情報ほど、上に置く。対応していない環境、制限の強いライセンス、向かない用途を、下に隠さない。
- 最初の画面(題、説明の1〜2文、動く例か入れ方)で、「何か」と「どう試すか」に答える。経緯や背景から始めない。
- 入れ方と最初の実行は、前提、コマンド、期待する結果の順に書く。入れ方が複数あるなら、既定の1つを先に書き、ほかは後ろか別の文書に置く。
- 見出しは、読者がやりたいことで付ける(「Pythonから使う」「ソースからビルドする」)。読者の属性(「Pythonユーザー」)で付けると、当てはまる読者が読み飛ばす。

## READMEと詳細文書の分担

| READMEに残す | 詳細文書へ移す |
|---|---|
| 上の問いへの答え、最初の成功までの手順、行き先の一覧 | 2つ目からの使い方、オプションやAPIの一覧、設計の説明、移行の手順、長いFAQ、変更履歴、ロードマップ |

- 消さずに移し、READMEに1行の行き先を残す。行き先は、やりたいことで書く(「引数の型を足す: `docs/arguments.md`」)。
- 移す先に同じ内容が既にあれば、2つを比べ、READMEにしか無い記述を移す先へ足してから、READMEの側を行き先に替える。
- 詳細文書が無い小さいプロジェクトでは、READMEに全部あってよい。分けるのは、1つの節が上の問いの答えを画面の外へ押し下げているとき。空の`docs/`を作らない。
- 貢献の手引き、行動規範、セキュリティの報告先は、決まったファイル(`CONTRIBUTING.md`など)に置き、READMEからはリンクする。
- READMEがレジストリのページやサイトのトップにも使われるなら、そこでの描画(相対リンク、HTML)を確かめ、`references/website.md`の「トップページの既定の問い」も合わせて見る。
- モノレポのルートのREADMEは、各パッケージのREADMEへの案内にする。

## 書いてよいこと

- 確かめられる事実だけを書く。「高速」「簡単」「強力」は、数値と条件、依存の数、対応環境の一覧など、読者が確かめられるものに替える。替えられなければ消す。
- 状態を盛らない。「production ready」や利用者の数は、根拠がリポジトリにあるか、利用者から得たときだけ書く。
- バッジは、第三者の検査が裏づけるもの(CI、公開している版、カバレッジ)を残す。意思を表すだけのもの(「PRs welcome」)は、何も伝えない。
- 手書きの目次は、見出しとずれやすい。残すなら、見出しと合っているかを確かめる。

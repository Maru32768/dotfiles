# 仕様書と設計文書

仕様書と設計文書(設計ノート、RFC)の仕事は、実装する人と変える人が、ある場合にどう動くべきかを引けること、なぜそう決めたかを知れること、変えると何に響くかを見積もれること。上から読み通す文書ではなく、引く文書として扱う。製品を使う人のためのリファレンスは、`guide.md`で扱う。

組み立て直すのは、置き場所と順だけ。規範と理由の記述は、文を変えずに移す。

- 元を変えずに、読む前に全体を把握したいだけなら、このスキルではなく`docs-overview`を使う。
- 受理した後は書き換えない決まりの文書(ADRなど)は、対象にしない。決まりが分からなければ、利用者に確かめる。

## 既定の問い

| 問い | 答えになるもの |
|---|---|
| これは何の仕様で、いまどの状態か | 対象、状態(案、採用、実装済み、置き換えられた)、対象外 |
| この場合は、どう動くべきか | 条件と結果。既定値、順序、制約、エラー |
| なぜこう決めたか。ほかに何を比べたか | 決定の理由、採らなかった案と、その理由 |
| ここを変えると、何に響くか | 依存する節、ほかの文書、コードの場所 |
| どこまで実装されているか | 実装済みのことと、予定や未決のことの区別 |
| 前の版から何が変わったか | 変更の履歴、移行の手順 |

問いは、仕様の中の具体的な場合で書く(「引数が省略されたとき、既定値はいつ評価されるか」)。「どう動くべきか」の問いは、端の条件と例外からも選ぶ。

## 記述の種類

台帳の記述の表に、種類の列を足す。コードや識別子だけでなく、地の文の条件と数値も記述として拾う。

| 種類 | 何か | 確かめる先 |
|---|---|---|
| 規範 | こう動く、こうでなければならない、という記述。条件、既定値、順序、制約、エラー | 文書そのもの。コードと食い違ったら、下の「食い違い」で扱う |
| 仕組み | いまの実装がどう作られているかの説明 | コード |
| 理由 | なぜそう決めたか。採らなかった案 | 文書、コミット、issue、書いた人。コードからは確かめられない |
| 予定 | まだ実装していないこと、未決のこと | 文書。実装済みかどうかは、コードで見る |
| 参考 | 例、図、注、経緯 | 例は、安全に実行できれば実行する |

どの種類か決められない記述は、規範として扱う。

## SKILL.mdと違う規則

次の規則は、SKILL.mdの同じ話題の規則の代わりに使う。

- **書き換えずに移す。** 規範、理由、予定の記述は、文を変えずに移す。まとめる、言い換える、短くする、表に組み替える、はしない。直してよいのは、移したことで合わなくなった指示語と相互参照(「上の表」「次の節」)だけで、直した行を変更表に書く。新しく書いてよいのは、冒頭の説明、節をつなぐ文、行き先の案内だけ。
- **削らない。** 「どの読者も行動を変えない記述」を、削る理由にしない。端の条件、対象外、採らなかった案は、めったに読まれなくても要る。削ってよいのは、一字一句同じ重複だけ。言い回しの違う重複は、食い違いの候補として両方を残し、報告する。
- **食い違い。** 規範の記述がコードと食い違っても、文書もコードも直さない。実装の誤り、古い仕様、まだ実装していない予定のどれなのかは、利用者にしか決められない。文書の行とコードの場所を挙げて報告する。仕組みの記述の食い違いは、SKILL.mdのとおりに、コードが正しいと言えるなら文書を直す。文書の中の食い違いも、どちらが正しいかを決めずに報告する。
- **理由を足さない。** 理由が書かれていない決定に、コードから推し量った理由を書かない。足してよいのは、出どころ(コミット、issue、利用者の説明)を示せる理由だけで、出どころを添える。
- **見出しを変えない。** 節の名前は、issue、PR、コミットメッセージ、ほかのリポジトリからも指される。そこのリンクは直せない。見出しの文言は変えず、順と階層だけを変える。節をほかのファイルへ移すときは、元の場所に見出しと1行の行き先を残す。見出しの改名と削除、ファイルの分割と統合は、利用者の承認を取る。
- **状態と履歴を消さない。** 状態の欄、日付、版、変更の履歴、置き換えの記述は、古く見えても残す。
- **図と表を足さない。** 頼まれたときだけ足す。足すなら参考と明記し、元の文を残す。節点、線、表の欄は、1つずつ元の文で確かめる。
- **点検。** コードの変更に合わせて規範の記述を書き換えるのは、その変更が仕様の変更だと分かるとき(PRの本文やissueに書かれている、利用者がそう言った)だけ。分からなければ、食い違いとして報告する。

## 構成

- 冒頭で、何の仕様か、状態、対象と対象外を言う。読む人ごとの入口(使う人はどの節、実装を変える人はどの節)も言う。冒頭の文は、本文にある記述だけで書く。
- 1つの文書が、外から見た振る舞い、内部の仕組み、決定の記録を抱えているなら、節で分け、どの節がどれかを冒頭に書く。
- 規範の本体は、引ける並びにする。項目の順を、APIやコードの構造か、処理の順に合わせる。

| 症状 | 直し方 |
|---|---|
| 経緯や前の状態の説明が、規範の本体より前に長く続く | 経緯の節を後ろへ移し、冒頭から行き先を示す |
| 理由と採らなかった案が、規範の文の間に挟まり、条件を引く邪魔になっている | 決定の節へ移し、元の場所に行き先を残す。邪魔になっていなければ、動かさない |
| 予定や未決のことが、実装済みの仕様と区別なく並んでいる | 文は変えずに、予定の節へ移す。どちらか決められない記述は、動かさずに報告する |
| 同じ規範が2か所にあり、言い回しが違う | どちらも残し、食い違いの候補として報告する |
| 用語が、定義より前に使われている | 定義の節を前へ移す。定義の文は変えない |

## 確かめる

SKILL.mdの6に、次を足す。

- **変わった行。** 前の版にあって、後の版のどこにも同じ行が無いものを挙げる。`lost.sh`が見ない地の文、表の行、見出しも入る。行の前後の空白は比べない。

  ```bash
  LC_ALL=C comm -23 \
    <(sed -e 's/^[[:space:]]*//' -e 's/[[:space:]]*$//' <work>/before/<ファイル> | LC_ALL=C sort -u) \
    <(cat <変えた後の関係するファイル>... | sed -e 's/^[[:space:]]*//' -e 's/[[:space:]]*$//' | LC_ALL=C sort -u)
  ```

  挙がった行は、1件ずつ変更表の行と対応させる(相互参照を直した、階層を変えた見出し、承認を得て変えた)。対応しない行は、元に戻す。一字一句同じ重複を削っても、同じ行が残るので挙がらない。段落を折り返して書いてある文書では、折り返しを変えると挙がるので、移す段落の折り返しを変えない。
- **意味の照合。** 挙がった行のうち、文を変えたもの(相互参照の直しも含む)があれば、書き手とは別のエージェントに、前の行と後の行を並べて渡す。主張、条件、数値、確度(できる、してよい、しなければならない)が変わっていないかを、1件ずつ判定させる。渡すのは、前後の行と、そのまわりの数行だけにする。文を変えた行が無ければ、起こさない。
- **読者テスト。** 細部の問いは、台帳の規範の記述から、端の条件と例外を選ぶ。

報告には、規範の記述とコードの食い違い、文書の中の食い違い、種類を決められなかった記述、挙がった行と変更表の対応を足す。

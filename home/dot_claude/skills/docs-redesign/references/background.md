# 設計の根拠

規則を足すとき、消すとき、測り直すときに読む。

## 1つのスキルにした理由

README、ガイド、Webサイトは、手順が同じで、既定の問いと置き場所の決まりだけが違う。違いは対象ごとの資料(`readme.md`、`guide.md`、`website.md`)に分け、要るものだけを読む。対象をまたぐ移動(READMEの詳細をガイドへ移す、サイトとREADMEの説明を揃える)が主な仕事の1つなので、スキルを対象ごとに分けると、その移動をどちらのスキルも持たない。

文の推敲は`prose-polish`が持つ。このスキルは文の規則を持たない。

## 調べた実装

2026-11-14に読んだ。表にコミットを書いたものはcloneして読み、書いていないものはその日のデフォルトブランチを取得して読んだ。どれも基盤にはせず、文も写していない。借りたのは考え方だけ。

既存のスキルをそのまま使わなかった理由。READMEだけならreadme-optimizationとreadme-skillsが使えるが、ガイドとサイトを扱わない。読者役のテストをするものは事実を確かめず、事実を確かめるものは読者役に試させない。構成を変えた後に、技術的な記述が残っているかを検査するものは無かった。

## 根拠にした研究と、使わなかったもの

使った。

- 開発者が文書で最も困るのは、内容の欠け、曖昧さ、誤りで、長すぎることは最も軽い(Uddin and Robillard 2015、IBMの開発者323人の調査)。優先順位を、事実、記述が残ること、たどり着けること、短さの順にした。
- READMEには「何か」と「どう使うか」はたいていあり、「なぜ選ぶか」と「いまの状態」は4件に1件ほどしか無い(Prana et al. 2019、393件)。READMEの資料で、欠けやすい問いとして挙げた。
- Diátaxisは、構成を上から決めずに1つずつ直すよう勧め、空の4区分を作ることを戒めている(diataxis.frのHow to use Diátaxis)。種類を分けすぎると情報が散る、という批判もある(Uddinの調査の断片化、Hillel Wayneの批判)。分類は診断の道具にとどめた。
- 階層の検証では、課題の文に行き先のラベルを入れない(NN/gのtree testing)。読者テストの問いに、見出しの言葉を使わないことにした。
- 宣伝の文を客観的な文に替えると、使いやすさが上がる(NN/g 1997)。古い調査で、製品サイトの技術者に限った結果ではない。サイトの資料で、宣伝の文を事実に替える規則にした。
- LLMに文章の質を採点させると、人の評価とほとんど合わない(arXiv 2504.07532)。提示の順、長さ、自分の文への好みで判定が動く(arXiv 2305.17926、2404.04475、2404.13076)。読者テストは質を採点させず、決めた問いに答えられたかと、引用が文書にあるかを数える。

使わなかった。

- READMEの特徴と人気の相関(arXiv 2206.10772)。相関でしかない。
- 最初の成功までの時間という指標。出どころが製品のブログだけで、研究が見つからなかった。
- 3クリックの法則、ナビゲーションの項目数の上限。根拠が無い。
- エージェントに導入の手順を実行させる検査。環境の準備で失敗することが多く(EnvBench、arXiv 2503.14443)、失敗が文書のせいかを人が見分ける必要がある。安全に実行できる手順を親が実行する形にとどめた。

## 検証(2026-11-14)

4つの文書を、リポジトリの写しの上で変えさせて比べた。対象はライブラリのREADME(1,515行)、同じライブラリのテストのガイド(340行)、このリポジトリのREADME(87行)、OSSのフレームワークのトップページ(MDCのコンポーネント)。

| 版 | 作り方 |
|---|---|
| スキル | opusのサブエージェントに、利用者の依頼の1文と、このスキルを読む指示を渡す |
| スキル無し | 同じ依頼の1文だけを渡す |
| readme-optimization | 同じ依頼に、samberのスキルを読む指示を渡す。ライブラリのREADMEだけ |

測り方は次の通り。スキルの中の読者テストとは別に行った。

- 問いと正解は、スキルを知らない別のopusが、変える前の文書とコードから作った。対象ごとに10〜12問で、文書に答えが無い問いを含む。
- 読者は版ごとに新しいsonnet。版には意味の無い記号を付け、どれが変える前かを伝えなかった。最初の50行だけで答える3問(何か、誰のためか、最初に何をするか)と、全部を読んでよい問いに答えさせた。
- 採点は別のopus。正解と比べ、引用が文書にあるかを`grep -F`で確かめた。
- ライブラリのREADMEとトップページでは、別のopusが新しく書かれた記述をコードと比べた。READMEでは、`lost.sh`が挙げた記述が後の版に残っているかも、1件ずつ確かめた。
- 落ちた記述の列は、`lost.sh`が挙げた記述のうち、意図せずに落ちていた件数。挙げた件数は、テストのガイドとこのリポジトリのREADMEのスキルの版が0件、トップページがどちらの版も1件。

| 対象 | 版 | 全部を読んだ正答 | 誤答 | 最初の50行(3問) | 新しい記述の誤り | 落ちた記述 |
|---|---|---|---|---|---|---|
| ライブラリのREADME | 変える前(1,515行) | 12問中11 | 0 | 1 | | |

| テストのガイド | 変える前 | 10問中8 | 0 | 1 | | |

| このリポジトリのREADME | 変える前 | 10問中7 | 0 | 2 | | |

分かったこと。

- 全部を読んだLLMの読者の正答の数は、前と後でほとんど変わらなかった。変える前の文書にも答えは書いてあり、LLMは1,515行でも最後まで読む。構成の良し悪しはこの数には出ない。
- 差が出たのは、最初の50行だけで答える3問と、誤った記述だった。トップページでは、変える前の版が根拠の無い数値を載せていて、読者がそのまま答えて2問を誤った。
- スキル無しの版との差は小さい。全部を読んだ正答の数は、同じか、1問の差だった。スキルの版は、新しく書いた記述の誤りが少なく(ライブラリのREADMEで0件、スキル無しは1件、readme-optimizationは3件)、頼まれていない変更(ファイル全体の表記の統一、コードブロックの書き換え)をしなかった。スキル無しの版は、トークンが7割ほど、時間が半分ほどで済んだ。スキルの版には、このほかに読者テストのサブエージェントが2つ(直した後に試し直せば3つ)かかる。
- 直す前のスキルは、スキル無しの版が直した誤りと欠けを見落とした。このリポジトリのREADMEでは、確かめた食い違いを「小さい」として残し、入口のスクリプトを読まなかった。ライブラリのREADMEでは、文書を名前で呼ぶリンクを2か所残した。どれにも規則を足した。このリポジトリのREADMEでやり直すと、食い違いを直し、スクリプトから欠けを補った。別に作った問いの正答は7から6で、差とはみなせない。文書を名前で呼ぶリンクの規則は、やり直しては確かめていない。
- 落ちた記述はライブラリのREADMEの3つの版のどれにも無かった。`lost.sh`が意図しない欠落を捕まえた例は、この検証には無い。スキルの版で挙げた131件はどれも別の書き方で残っていたので、`lost.sh`の出力で、語が残っている行を`line`という種類に分けた。件数は検証のときの`lost.sh`のもの。その後のレビューで一致の判定を直したスクリプトでは136件が挙がり、増えた5件も別の書き方で残っていた。
- スキルの版も条件つきの既定を言い切る誤りを1件書いた(トップページ)。分岐まで読む規則を足したが、やり直しては確かめていない。

限界。

- 人の読者では確かめていない。短くしたこと(1,515行から224行)が人に効くかは、測れていない。LLMの読者は、開くファイルが1つから9つに増えても同じ数だけ答えた。
- 対象は4つで、版ごとに1回しか試していない。1問の差は差とみなさない。
- 書き手、読者、採点者、正解を作った者が、同じ系列のモデルである。
- 正解を作った者が思いつかない問いは測れない。
- テストのガイドと、このリポジトリのREADMEでは、新しい記述を独立には確かめていない。READMEの直した後の版だけは、親がスクリプトを読んで確かめた。

測り直すときは、上の作り方と測り方をそのまま使う。

## 仕様書と設計文書(2026-11-15)

仕様書と設計文書の規則(`spec.md`)は、設計ノート1本で1回試して決めた。

README、ガイド、Webサイトの規則のうち、次の6つは仕様書に合わない。違いを`spec.md`に分けた。

| 元の規則 | 仕様書で起きること |
|---|---|
| 食い違いは、コードを正として文書を直す | 仕様書は、どうあるべきかを書く。食い違いは、実装の誤り、古い仕様、まだ実装していない予定のどれかで、文書を直すとは決められない |
| 書いてよいのは、コードで確かめた事実だけ | 決定の理由と採らなかった案は、コードからは確かめられない |
| どの読者も行動を変えない記述は、削ってよい | 仕様書は引く文書で、端の条件や対象外は、めったに読まれなくても要る |
| 落ちた記述は`lost.sh`で挙げる | `lost.sh`が見るのは、コード、インラインコード、リンク。条件や数値は地の文にある |
| 見出しを変えたら、リンクを直す | 節の名前は、issueやPRなど、リポジトリの外からも指される |
| 読者テストの既定の問い | 仕様書の問いは、この場合どうなるか、なぜこうしたか、変えると何に響くか |

規範の記述を書き換えずに移すことにした根拠。

- LLMの要約は原文より広く言う(Peters and Chin-Yee、arXiv 2504.00025。親が要旨で確かめた)。docs-overviewを試したときも、概観の文を書かせると誤りが出て、親が直すと新しい誤りが入った(docs-overviewの`references/background.md`)。
- AIが書き換えた文書は、意味が変わっていないかを見直す必要がある、とされている(Thoughtworks Technology Radar、2026-11-04、「Semantic review of AI-edited prose」をAssessに置く。親が確かめた)。文を変えなければ、変わっていないことを行の比較で確かめられる。

ADRを対象にしないのは、受理した後は書き換えずに新しいADRで置き換える流儀が多いため(サブエージェントの報告で、元は確かめていない)。

試し方と結果。

- **題材。** CommandLibの`docs/design`(コミット`4edf11e8`)の設計ノート1本、315行。経緯、API、実装、移行、段階、決定が1つの文書に入っている。地の文は約120字で折り返してある。
- **作り方。** `SKILL.md`と`spec.md`の下書きだけを読ませたエージェント(opus)に、写しを再構成の深さで組み立て直させた。
- **結果。** 経緯の2つの節(49行)を末尾へ移し、冒頭に入口の段落(6行)を足した。見出しの文言と階層は変えていない。空行が1つ増え、322行になった。
- **行の検査。** 前の版の行で、後の版に同じ形で残っていないものは2行。相互参照をリンクにした行と、仕組みの表のセルをコードに合わせて直した行。親が回し直して同じ結果を得た。直したセルは、親がコードで確かめた。`lost.sh`が挙げたのは、同じセルの1件。
- **独立の照合。** 前後の版だけを読ませた別のエージェント(opus)は、落ちた記述を0件、書き換わった記述を同じ2行とした。新しく書いた5文は本文に支えられていたが、1文は節の中身を言い直して条件を落としていた。指示語と番号の指す先は変わっていなかった。移した節が説明していた名前が4つ、説明より前に出るようになっていた。文書内のリンク13件は見出しに当たった。
- **読者テスト。** LLMの読者(sonnet)は前の版でも後の版でも、12問のうち12問に正答した(採点は書き手)。見出しだけの部は、どちらも11問のうち9問が当たりだった。
- **書き手が挙げた食い違い。** 規範の記述とコードの食い違いが2件、文書の中の食い違いの候補が3件、種類を決められなかった記述が1件。規則のとおり、どれも直さずに報告した。規範とコードの食い違いのうち1件は、親がコードで確かめた。
- **トークン。** 書き手が18万(中で起こした読者2つと意味の照合は含まない)、独立の照合が10万。通知に出た値。

分かったこと。

- 書き換えずに移した記述からは、落ちも、意図しない意味の変化も出なかった。疑いが出たのは、新しく書いた文だけだった。
- 行の検査と独立の照合は、書き換わった行として同じ2行を挙げた。落ちと書き換えを見つけるには、行の検査で足りた。置き場所が変わった影響(説明より前に出る名前)と、新しく書いた文が本文に支えられているかは、行の検査では分からない。
- 構成の差はLLMの読者の正答の数には出なかった。上の検証と同じ結果。
- 書き手は手順書で迷った点を11件挙げた。

実行の後で直した規則。直した後の規則では、組み立て直させていない。

- 仕組みの記述をコードに合わせて直した行を、行の検査の対応先に入れ、意味の照合からは外すこと。
- 規範と仕組みの境目(外から見える面か、中の作りか)。
- 移した節をまとめる見出しを足してよいこと。経緯の移し先。
- 読者テストの細部の問いの選び方と、見出しを複数挙げた答えの採点(`reader-test.md`)。
- 文書が一覧にしている公開の面を、コードと突き合わせること。
- 行き先の案内で、節の中身を言い直さないこと。
- 節を後ろへ移すとき、その節が説明していた用語に行き先を足すこと。
- レビューで直した規則。推敲に渡すのを新しく書いた行に限ること。どの種類の記述も書き換えず、段落を割らずに移すこと。上の独立の照合を、手順に入れたこと(試しでは、親が同じ形のプロンプトで起こした)。行の検査で、字下げと同じ文言の行の数も比べること(試しの前後では、同じ2行が挙がる)。点検の頼まれ方と、節を別のファイルへ移すときの承認。

限界。

- 1本を1回しか試していない。題材は実装済みの設計ノートで、規格の形の仕様書(「しなければならない」を並べる文書)は試していない。
- 題材は折り返して書いた文書で、書き手は折り返しを変えずに移した。折り返しを変えたときに行の検査がどう挙げるかは、試していない。
- 全体の深さ(複数の仕様書をまたぐ移動)と、点検の規則は試していない。
- 書き手が挙げた食い違いのうち、親が確かめたのは1件だけ。
- 見出しの文言を変えず、記述も書き換えないので、できる組み立て直しは、並べ替え、階層の変更、案内や見出しを足すことに限られる。
- 人が引きやすくなったかは、測っていない。書き手、読者、照合が、同じ系列のモデルである。

# エージェントの開発の流れ

`home/dot_claude/skills/`の`ship-task`、`review-loop`、`split-pr-stack`が作る開発の流れと、2026-11の見直しで何を測り、何を決めたかを書く。モデル、Claude Code、GitHubは変わり続けるので、ここに書いた手順で定期的に測り直す。

## 今の形

- **ship-task。** 完了条件を例つきで言い直し、実装の前にスライス(単独で検証でき、単独で着地させてよい変更)に分ける。スライス表はissueに置く。スライスごとに、実装、完了条件の突き合わせ、review-loop、着地(直接、PR、チームのPR)を回す。最後に、元の完了条件を着地した先端で突き合わせる。
- **review-loop。** 片づけ(ponytail-review、simplify、推敲)を先に済ませ、R1でOpusの2トラック(correctnessとテスト品質)を並列に読ませる。親が再現してから直し、R2で修正の差分を確かめる。ラウンドは3回まで。収束したらFableとCodexに1回ずつ読ませ、最後に`scripts/evidence.sh`で、検証が最後のツリーで通っていることを確かめる。深さは変更のリスク(軽、通常、高)で変える。
- **split-pr-stack。** 既にある大きいブランチを、後から層に分けるときだけ使う。業務のリポジトリのチームの決まり(ベースPR、子issue、Sprint、QA)に合わせるため、ベースPRに子PRを集める形は変えていない。

外の研究と実装から借りた根拠と、借りなかった根拠は次のとおり。

- 使えた根拠: エージェントが書いたテストは、通っても欠陥を拾わないことが多い(TestSuiteBench、arXiv 2610.13065)。テストを書き換えて通す不正は、テストを読み取り専用にすると止まる。テストの特別扱いは止まらない(ImpossibleBench、arXiv 2510.20270)。同じモデルの独立した再レビューを合算すると、1回だけより悪くなる(arXiv 2603.16244。単著の1件)。並列に書くエージェントは成功率を下げる(CooperBench、arXiv 2601.13295)。
- 使えなかった根拠: 別のモデルの補完性(arXiv 2607.21656)は、弱い下書きを見直す効果と区別できなかった。SkillsBench(arXiv 2602.12670)の領域別の数字は、版が上がって変わっていた。最新の版(v4)からは、短く絞ったSkillが効き、網羅的なSkillはほぼ効かず、モデルに作らせたSkillは害になる、という向きだけを借りた。
- 調べた実装(2026-11-13のコミット): obra/superpowers `22f0b463`、EveryInc/compound-engineering-plugin `41216b7e`、garrytan/gstack `4414f4cc`、citypaul/.dotfiles `cd4028d5`、mattpocock/skills `5863806d`、github/spec-kit `2ee2b1e8`、github/gh-stack `bd0a3250`、Fission-AI/OpenSpec `d12c2817`、anthropics/claude-plugins-official `f75f5b25`、anthropics/skills `2c5958ec`。どれも基盤にはせず、考え方だけを借りた。台帳と再開の規約(superpowers)、証拠を作業ツリーの指紋に結びつけること(gstack)、深さを結果の重さで決めること(compound-engineering、gstack)、要求とPRの境界を分けて考えること(citypaul)。

## 測り直す

次のどれかが起きたら測り直す。

- 既定のモデルの世代が変わった
- Claude Codeの、Skillの読み込み、圧縮、サブエージェントの扱いが変わった
- GitHubの、Stacked PRやレビューの機能が変わった
- 前に測ってから、スライスが20個ほど着地した

### 台帳の印を数える

review-loopの台帳(`ledger.md`)の「対応済み」「見送り」「申し送り」「却下」の行には、`[工程/重大度/由来]`の印が付いている。工程と由来ごとの件数は、次で数える。

```bash
awk '/^# /{s=($0 ~ /^# (対応済み|意図的に見送り|申し送り|却下)/)} s' ledger.md \
  | grep -o '^- \[[^]]*\]' | sed 's/^- \[//; s/\]$//' \
  | awk -F/ '{n=split($1,a,"+"); for(i=1;i<=n;i++) c[a[i]"/"$3]++} END {for (k in c) print k, c[k]}' | sort
```

台帳はセッションのscratchpadにあり、セッションが終わると消えることがある。数えたい台帳は、review-loopの最終報告にあるパスから写しておく。

工程を消すか残すかは、次で決める。

- 10スライス続けて、開始時からの欠陥(由来が`start`)を1件も出さず、費用が全体の5%を超える工程は、既定から外す候補にする
- SKILL.mdに規則を足すときは、元になった指摘を添える。その種類の指摘が20スライス出なければ、規則を消す候補にする

### 過去の実行に当て直す

ある工程を動かしたときの効果は、過去の実行に当て直して測る。2026-11のV1(FableとCodexをR1に移せるか)は、次の手順で測った。

1. 下の評価セットの実行ごとに、R1の入力のSHAを`git worktree add --detach`で取り出す
2. 試したいレビュアーに、`<base>...<R1の入力のSHA>`を1回読ませる。台帳、後で見つかった欠陥、測る目的は渡さない
3. 後で見つかった欠陥と、同じファイルの同じ症状の指摘が出たかを数える

気をつけること。

- 対象のリポジトリはどれも公開なので、学習データに入っている恐れがある
- 今の`~/.claude/CLAUDE.md`やSkillに、後で入った修正の文があると、レビュアーの文脈に答えが入る。その項目は分けて数える
- 1件につき1回しか回さないと、「出なかった」は「この1回では出なかった」の意味にしかならない
- 標本は10件ほどなので、割合の差には意味が無い。個別の事例として読む

## 決めていないこと

- 台帳を、別のセッションから見つけられる置き場にするか。リポジトリの`.git`と`.claude`は、Claude Codeの保護パスで使えない。作業ディレクトリの外に置くなら、`permissions.additionalDirectories`に足す必要がある
- GitHubのStacked PRへの登録(`gh stack link`)は試していない。`gh stack`のローカルの操作(`push`、`submit`)は、リモートにしか無い変更を上書きしうるので使わない
- Codexのモデル(`gpt-6-astra`)とeffort(`high`)は、ほかの組み合わせと比べていない。Codexの費用はClaude Codeのログに残らない
- split-pr-stackは、複数のスライスに分けた仕事を10件進めて一度も使わなければ、消す候補にする
